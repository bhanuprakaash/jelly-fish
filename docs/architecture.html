Five rules that explain everything

  1. Postgres is the only thing api and worker share. There's no Redis, no queue and no RPC. They never talk to each other directly.
  2. The events table is the source of truth. The sessions row (status, last_seq, title, tokens) is a projection of it, updated in the same transaction.
  3. A NOTIFY is a hint, not data. Whoever receives jf_events, jf_activity or jf_runnable re-reads Postgres. Lost hints are covered by polls and pings.
  4. Token deltas are ephemeral. They travel over jf_stream and are never stored. The durable reply is the llm.response event.
  5. Only one Worker advances a session at a time. A Lease plus an epoch fence enforce this: every Worker write checks lease_owner + lease_epoch + lease_expires_at.

2Postgres as the message bus

There are four LISTEN/NOTIFY channels. A NOTIFY sent inside a transaction is delivered only after commit, so a hint can never point at a row you can't read yet.

channelpayloadsent bylistened bywhat the listener does
jf_runnable<session_id> CreateSession; any append whose status change goes to runnable (user message, retry, model change); Store.Release every worker (worker.listen) Pokes the claim loop: wake <- struct{}{} → claimAll. The hint carries no ownership. The Claim SQL decides who gets the session.
jf_events<session_id>:<seq> every append (api or worker) and every Claim, via notifyAppend every api pod (stream.Listen) hub.Notify(sid) → each open Session stream for that sid runs ListEvents(seq > lastSent) and writes SSE frames.
jf_activity<user_id>:<session_id> appends containing session.status_changed or session.created (Claim included) every api pod hub.NotifyActivity(user, sid) → the Activity stream runs ActivityStatusOf(sid) and writes event: status. If the queue is full it resyncs with a snapshot instead.
jf_streamJSON Delta (under 7900 B; longer text is split) worker Batcher, every 50ms, outside any tx (pool.Exec) every api pod bus.deliverPayload → subscriber channels → event: delta frame. Deltas are never stored, so a missed one is gone.

Why one LISTEN connection in api matters

A connection receives notifications in commit order. Before appending llm.response, the worker calls stopBatch(), which flushes the last delta. So the api sees the turn's last delta before the jf_events hint for the final reply. The Session stream also drains queued deltas (pendingDeltas) before writing durable frames.

internal/stream/listen.go · internal/api/sessions.go

Lost hints are fine

  • worker: polls Claim every 3s anyway. Timers (wake_at) and expired leases are only found by this poll.
  • api Listen drop: re-LISTENs after 3s, then hub.hintAll(). Every session stream re-queries and every activity stream gets a fresh snapshot.
  • Session stream: a 15s ping also re-queries seq > lastSent and re-checks the Login Session.

Multiple api pods

Each api pod runs its own Listen and gets every notification, then routes it only to the streams it holds. Scaling api out needs no coordination. The per-user cap of 20 streams is counted per node.

Watch it

jf_pg_notification_queue_usage is the fraction of Postgres's NOTIFY queue in use. It grows if some listener stops reading. jf_stream_deltas_dropped_total counts deltas dropped for slow browsers.

6Worker: drive loop, lease & fence

This is durable execution on Postgres (ADR 0001). A drive is a pure function of the event log plus side effects, and every side effect is written back as events through a fence.

The loop

↓
claimAllWhile a slot is free (50 max): Store.Claim(owner=host:pid, ttl, skip=released). Each claim gets its own goroutine.
↓
drive(claim)Starts a heartbeat goroutine. If recovery_attempts > 5, it fails the session with crash_loop.
↓

↓

internal/worker/worker.go · fold.go · decide.go

Claim (one tx)

WITH c AS (SELECT id, status FROM sessions
  WHERE status='runnable'
     OR (status='sleeping' AND wake_at <= now())
     OR (status='running'  AND lease_expires_at < now())
  ORDER BY ready_at NULLS LAST
  FOR UPDATE SKIP LOCKED LIMIT 1)
UPDATE sessions SET status='running', lease_owner=$me,
  lease_epoch = lease_epoch+1, lease_expires_at = now()+30s,
  recovery_attempts = recovery_attempts+1, wake_at=NULL, last_seq += 1|2

The same tx inserts timer.fired (if the session was sleeping) and status_changed → running, then NOTIFYs activity and events.

Fence: every worker write

AppendFenced adds this to the UPDATE sessions SET last_seq…:

WHERE lease_owner=$me AND lease_epoch=$epoch AND lease_expires_at > now() and, for parks, AND last_seq = $expectSeq

  • 0 rows and the fence still holds → ErrStale: new events arrived (e.g. a user message mid-turn), so re-fold and go again.
  • 0 rows otherwise → ErrLeaseLost: someone else owns it, so write nothing more.
  • Success resets recovery_attempts = 0.

Heartbeat (every JF_HEARTBEAT=10s)

UPDATE … SET lease_expires_at = now()+TTL WHERE fence RETURNING cancel_requested

  • Lease lost → cancel(ErrLeaseLost). The in-flight LLM call dies.
  • cancel_requested → cancel(errInterrupted) → finishInterrupt: turn.interrupted + awaiting_user.

Parking clears the lease

Any status change away from running also sets lease_owner = NULL, lease_expires_at = NULL and cancel_requested = false. Only a Claim sets a lease.

The database is the clock

Lease expiry, wake_at (now() + interval) and timer.set all use Postgres now(), so workers don't need to agree on the time.

Idempotency keys

  • session_id is minted by the client. Repeating the create returns the existing last_seq, and a unique-violation falls back to the existing row.
  • client_msg_id has a unique index on events(session_id, payload->>'client_msg_id') WHERE type='user.message'. A duplicate POST returns the original seq.
  • turn_id is set as correlation_id on turn.started, llm.response, usage and session.error.

Login (passwordless)

  • POST /api/auth/code always answers 202. Invited users get a code and a link by SMTP. Only sha256 hashes are stored in login_codes.
  • Verifying creates a login_sessions row (token_hash) and sets the HttpOnly cookie __Host-jf_login (SameSite Lax).
  • authn on every /api request has a sliding expiry. Open streams re-check LoginActive every 15s, so "log out everywhere" also kills SSE.

Tenancy

Every Repo method takes a TenantScope{WorkspaceID, UserID} (enforced by a test). Another tenant's session looks exactly like a missing one: ErrNotFound, 404. The worker's Store isn't scoped, because the claim and the fence already authorize it.

10What happens when…

The same machinery covers the failure paths: write events through the fence, change status, and let the NOTIFY hints update the UI.

…Anthropic is flaky (429/5xx)

  1. In-process: retry.Wrap retries up to 4× (1, 2, 4, 8s). Each retry sends a reset delta and the browser drops the partial bubble. Each attempt gets a span.
  2. Still failing → the session sleeps: one tx with usage + session.error{retryable:true} + status → sleeping + timer.set{wake_at}. Backoff by RetryStep: 1m → 5m → 15m.
  3. The worker's 3s poll claims it when wake_at ≤ now() → timer.fired + running → the turn re-runs.
  4. After the third sleep → status → failed (retries_exhausted). A user message resets RetryStep.

…the error isn't retryable

key_invalid, billing, model_unavailable, too_large and bug each write session.error{retryable:false} with a fixed message (provider text is never stored) → awaiting_user.

Retry (POST /retry) works only if the last non-status event is that stop error. Changing the model resumes on its own after model_unavailable or billing.

long_wait (the provider asked for a pause) writes turn.interrupted{provider_wait} → sleeping for retry-after, with no error.

…the user hits Stop

POST /interrupt appends user.interrupt.

  • running: sets cancel_requested = true. The worker's next heartbeat (≤10s) cancels the context, the stream aborts, and finishInterrupt writes turn.interrupted{user_interrupt} + awaiting_user.
  • sleeping ("Stop retrying"): goes straight to awaiting_user.
  • Any other status: nothing happens.

…a worker pod dies mid-turn

Heartbeats stop and the lease expires after 30s. The other pod's poll claims the session (epoch+1). Decide sees an OpenTurn → turn.interrupted{worker_lost} → a new turn re-runs from the same input. If a session's claims die 5 times in a row without one fenced write → failed{crash_loop}. make chaos tests this.

…the user sends a message mid-turn

POST /messages appends user.message. The status change has From: awaiting_user|sleeping|completed|failed, so a running session stays running (no jf_runnable). The turn finishes, the park's ExpectSeq no longer matches → ErrStale → re-fold → PendingUserSeqs → another turn.

…a deploy ships a new event schema

An old worker that loads an event with a schema_version it can't upcast Releases the lease (expires it now and NOTIFYs jf_runnable) and writes nothing. It skips that session for 1 min, and a newer worker claims it. Releasing doesn't count toward crash_loop.

…the api loses its LISTEN connection

Deltas sent meanwhile are lost (the UI tolerates this, and the final llm.response is durable). After 3s it re-LISTENs and calls hintAll(): session streams re-query, and activity streams get a resync snapshot.

…the browser is slow or hidden

A full delta buffer marks that turn as gapped for that tab only. A write over 10s closes the stream, and EventSource reconnects with Last-Event-ID. A hidden tab closes both streams. On show it reopens with ?after=lastSeq and a fresh activity snapshot.

…the user renames during the auto-title

PUT /title appends session.renamed{by:user}, unfenced and under the row lock. When the title call's append arrives, dropSupersededAuto removes its rename but keeps its usage. The user's rename always wins.
