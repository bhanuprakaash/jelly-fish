# MCP Client and OAuth: Research

Status: research, 2026-09-27. Terms follow [`CONTEXT.md`](../../CONTEXT.md): an MCP server attached to a project is a **Connector** (never "integration/MCP/plugin"), remote (a URL, optionally behind OAuth) or local (stdio, **Sandbox**-only). A question a Connector asks mid tool-call is an **Elicitation** (never "prompt/form"). Facts cite primary sources inline. **Unverified** marks anything not confirmed from a primary source. "⚠ cross-spec" flags a conflict or gap against an existing ADR/design doc or against jelly-fish's own assumptions; flagged here, not resolved.

> Ground truth, not redesigned here: [product.md](../product.md) ("An MCP client using the official Go SDK"; "Remote connectors over Streamable HTTP, with an OAuth 'Connect' flow plus custom URL and headers"; "Local (stdio) connectors run only inside the sandbox"; "MCP tools plus elicitation (which reuses the approval UI)"; Provider Keys envelope-encrypted, decrypted only in the Worker), ADR [0003](../adr/0003-nothing-executes-on-the-host.md) (local stdio Connectors run only inside the Sandbox; remote ones are called from the Worker over HTTP), ADR [0004](../adr/0004-layered-approver-no-implicit-rules.md) (`readOnlyHint`/`destructiveHint` seed Approver defaults), [agent-loop.md](../design/agent-loop.md) §5.6 (`input_required` multi round-trip via `elicitation.requested`/`elicitation.resolved`; legacy `elicitation/create` holds the Worker up to 5 min; MCP cancel via ctx/`notifications/cancelled`; Decision 16, 21), [event-log.md](../design/event-log.md) (event catalog rows `elicitation.requested{connector, schema}`/`elicitation.resolved{answer}`, §5.18; secrets never enter payloads), [provider-gateway.md](../design/provider-gateway.md) (tool results are `[]msg.Part`; MCP tool schemas sent non-strict), [context.md](../design/context.md) (project files index in the prompt, read via `read_upload`), [TODO.md](../../TODO.md) (this item must cover the `input_required` payload/resume shape and the legacy 5-min hold), [research/sandbox.md](sandbox.md) §9 (stdio Connector supervision across a Worker crash, Q8) and §13 (whether Connector secrets enter the Sandbox, Q10).

## 1. Summary

- **The MCP spec had a major rewrite on 2026-07-28** (current revision), abandoning the `initialize` handshake, protocol-level sessions (`Mcp-Session-Id`), and stream resumability (`Last-Event-ID`) entirely, in favor of **per-request protocol versioning** and a new **Multi Round-Trip Requests (MRTR)** pattern ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). This is not a minor point release — it changes almost every mechanic this doc was asked to cover, and postdates this agent's own training data, so every claim below was fetched and re-verified live against modelcontextprotocol.io rather than assumed.
- **MRTR is an unexpectedly close match for jelly-fish's `input_required` design.** Under MRTR, a server that needs input from the client no longer sends its own JSON-RPC request; it returns an `InputRequiredResult` (`resultType: "input_required"`) from the original call, carrying the pending requests (e.g. `elicitation/create`) and an opaque `requestState` blob. The client later **retries the original request** (new JSON-RPC id, same arguments) with `inputResponses` + the echoed `requestState` ([MRTR spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)). This needs no shared server-side storage across retries by design — exactly the property jelly-fish's Postgres-only, Worker-less parking model needs (§7).
- **Sampling and Roots are now spec-deprecated** ("new implementations should not add support," suggested migration: "integrate directly with LLM provider APIs instead of Sampling" — [changelog §Deprecated](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). ⚠ cross-spec: [product.md](../product.md)'s "Later roadmap" lists "MCP resources, prompts and sampling" as a future item; Sampling is a feature MCP itself is walking away from, and jelly-fish already has an equivalent (Provider Gateway) — flagged as Q9 below.
- **Dynamic Client Registration (RFC 7591) is now deprecated in favor of Client ID Metadata Documents (CIMD)** — a client hosts its own metadata JSON at an HTTPS URL that *is* its `client_id`; the authorization server fetches and validates it on demand, no registration call needed ([client-registration spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). DCR remains as a fallback only.
- **The MCP spec directly answers one of [sandbox.md](sandbox.md)'s open questions (Q10):** for stdio transport, "implementations ... **SHOULD NOT** follow this specification, and instead retrieve credentials from the environment" ([authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)) — i.e. a local Connector's own credentials belong in the Sandbox process's environment variables, not behind an OAuth flow. See §7.4.
- It also bears on sandbox.md's Q8 (stdio Connector supervision across a Worker crash): the stdio transport section says a client "**SHOULD** restart" a server that exits unexpectedly, and because the protocol is now stateless, "in-flight requests are lost; client retries against fresh process" ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)) — the spec itself expects exactly jelly-fish's existing "never auto-retry a tool call, respawn clean" posture. See §7.4.
- Real-world Connectors will lag this rewrite for a long time (it is weeks old as of this research). jelly-fish's Go SDK-based client must speak both eras: the modern stateless/MRTR wire format, and the legacy `initialize`-handshake, server-initiated-request era (2025-11-25 and earlier) that most deployed servers still speak today. The "legacy `elicitation/create`" jelly-fish's own docs already call out is this older era, not a hypothetical.

## 3. Client lifecycle and protocol versioning

- **Current model (2026-07-28, no handshake)**: every request carries `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in `_meta`; servers accept or reject **per request**, independently. Clients/servers MAY support multiple versions at once. A version mismatch returns `UnsupportedProtocolVersionError` (JSON-RPC code `-32022`) listing what the server supports ([versioning spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).
- **`server/discover`**: a mandatory RPC returning a server's supported versions, capabilities and identity in one call. Calling it is optional — a client can just send a request and handle a version error (same source).
- **Also removed/moved in 2026-07-28**: `ping`, `logging/setLevel` and `notifications/roots/list_changed` are gone (log level is now per-request `_meta`); URL-mode `notifications/elicitation/complete` and `elicitationId` are gone (the client learns the outcome by retrying; servers correlate via `requestState`); experimental tasks moved to an official extension `io.modelcontextprotocol/tasks` (polling via `tasks/get`, input via `tasks/update`) ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) major 5–6, minor 11). Liveness for remote Connectors can't rely on `ping` for modern servers.
- **Legacy model (2025-11-25 and earlier)**: the client **MUST** send `initialize` first (`protocolVersion`, `capabilities`, `clientInfo`), the server responds with its own capabilities, then the client sends `notifications/initialized` before any other request ([2025-06-18 lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle) — text unchanged since; direct quote of the three-message flow). Capability negotiation there is the client declaring `roots`/`sampling`/`elicitation`/`experimental`, the server declaring `prompts`/`resources`/`tools`/`logging`/`completions`/`experimental` (same page).
- **Backward-compat detection**: a client speaking both eras tries a modern request first; on HTTP 400, it inspects the body — a recognized modern JSON-RPC error (`UnsupportedProtocolVersionError`, `MissingRequiredClientCapabilityError`, `HeaderMismatch`) means "modern server, retry correctly"; an unrecognized/empty body means "legacy server, send `initialize`" ([Streamable HTTP backward-compat](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#backward-compatibility)).
- **Cancellation**: `notifications/cancelled{requestId, reason?}` on stdio; on Streamable HTTP, closing the SSE response stream *is* the cancellation signal, no message is sent or expected ([cancellation pattern](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation)). This matches agent-loop.md Decision 21 exactly ("cancel `ctx`; Go SDK handles stdio notify / HTTP stream close").
- **Progress**: opt-in via a `progressToken` in `_meta`; `notifications/progress{progressToken, progress, total?, message?}`, `progress` must increase monotonically (same page). Implementations MAY reset a timeout clock on progress but MUST still enforce a maximum regardless.
- **Timeouts**: the spec does not mandate a number — "Implementations **SHOULD** establish timeouts for all sent requests" (same page) — consistent with jelly-fish already owning its own tool timeout (`ToolDef.Timeout`, agent-loop.md Decision 11) rather than waiting on an MCP-specified value.
- **Go SDK**: the official SDK (`modelcontextprotocol/go-sdk`) shipped **v1.7.0 (2026-07-28)** with "full support for protocol version 2026-07-28" including the stateless architecture and MRTR/`InputRequiredResult`; the current stable is **v1.8.0 (2026-09-14)**, whose release notes describe hardening transports "against resource exhaustion, closing session leaks, deadlocks and teardown hangs" ([releases](https://github.com/modelcontextprotocol/go-sdk/releases)). Client shape: `mcp.NewClient(impl, opts) *Client`, `.Connect(ctx, transport, opts) (*ClientSession, error)`, with `ClientSession.CallTool/ListTools/Ping/...` ([client.go](https://github.com/modelcontextprotocol/go-sdk/blob/main/mcp/client.go)). Context cancellation is translated automatically into `notifications/cancelled`/stream-close, with the caveat that "there's a guarantee that the cancellation notification has been sent, but there's no guarantee that the server has observed it" ([go-sdk protocol.md](https://raw.githubusercontent.com/modelcontextprotocol/go-sdk/main/docs/protocol.md)) — this is the same "may still have partially run" caveat agent-loop.md §5.4 already assumes for interrupted MCP calls, so no change needed there.
- **Unverified**: the exact Go SDK API surface for registering handlers under MRTR (an `ElicitationHandler`/`InputRequiredHandler` on `ClientOptions`) was reported by one research pass but not independently confirmed against the SDK source in this pass; treat the *existence* of MRTR support in v1.7.0+ as confirmed (per the release notes above) and the exact type names as **Unverified** until read directly off `main`.

## 4. Transports

| | stdio | Streamable HTTP (current, 2026-07-28) | HTTP+SSE (2024-11-05, deprecated) |
|---|---|---|---|
| Framing | One JSON-RPC message per line over stdin/stdout; stderr is free-form logs, not an error signal ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)) | Every JSON-RPC message is its own HTTP POST to one **MCP endpoint**; response is `application/json` or an SSE stream scoped to that one request ([streamable-http](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)) | Separate GET (SSE stream) + POST endpoints |
| Sessions | N/A (one process per client) | **Removed.** No `Mcp-Session-Id` header, no protocol-level session at all; `tools/list` etc. must not vary per-connection ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) item 1, [SEP-2567](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2567)) | `Mcp-Session-Id` header, terminated with HTTP DELETE |
| Resumability | N/A | **Removed.** "Resumable SSE streams via `Last-Event-ID` are not supported" — a broken stream loses the in-flight request; the client **MUST** re-issue it as a new request with a new id ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) item 9) | Resumable via `Last-Event-ID` + SSE event ids |
| Server-initiated input | N/A | **Not delivered as a request at all** — embedded as `inputRequests` inside an `InputRequiredResult` per MRTR (§7) | Server could send a JSON-RPC *request* on the SSE stream |
| Long-lived change notifications | via a subscription-style loop over the same pipe | `subscriptions/listen`: one long-lived POST-response stream the client opts into per notification type (`toolsListChanged`, `resourcesListChanged`, ...); acknowledged, then the server tags each notification `io.modelcontextprotocol/subscriptionId` ([streamable-http](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)) | replaced the standalone GET stream |
| Security | n/a (local process) | Servers **MUST** validate `Origin` (DNS-rebinding), **SHOULD** bind to `127.0.0.1` when local, **SHOULD** authenticate all connections (same page) | same |
| Status | current | current | Deprecated since 2025-03-26, formally **Deprecated** feature-lifecycle state as of 2026-07-28, "eligible for removal in a future revision" ([SEP-2596](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2596)) |

- **Shutdown**: stdio — close stdin, wait, `SIGTERM`, then `SIGKILL` if still alive; HTTP — close the connection(s). No MCP-level shutdown message exists ([lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle), unchanged mechanics in 2026-07-28).
- **Unexpected stdio server exit**: "the client **SHOULD** restart it. Because the protocol is stateless, in-flight requests are lost; client retries against fresh process" ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)) — see §7.4 for how this resolves sandbox.md's Q8.
- **New request-metadata headers**: Streamable HTTP now mirrors selected body fields into `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` headers (and optionally per-parameter `Mcp-Param-{Name}` via an `x-mcp-header` schema extension), so intermediaries can route/inspect without parsing bodies; header/body mismatches are rejected with `400` + `HeaderMismatch` (`-32020`) (same page). Not architecturally significant for jelly-fish's client, but worth knowing before writing an HTTP client wrapper: these headers are **required**, not optional decoration.
- ⚠ cross-spec: none of jelly-fish's docs mention `Mcp-Session-Id` or session affinity for remote Connectors, so there was nothing to break here — but any implementation notes drafted against pre-2026-07-28 MCP tutorials (most blog posts and even some vendor docs still describe session ids) will be wrong for a server actually speaking the current revision. The Go SDK's backward-compat probing (§3) is the only reliable way to know which era a given Connector speaks.

## 5. Tools (and why resources/prompts stay deferred)

- **`tools/list`** supports pagination (`cursor`/`nextCursor`) and now also **`ttlMs`**/**`cacheScope`** ("public"/"private") cache hints on every list/read result via a `CacheableResult` interface, added specifically so clients can cache tool lists and "improve LLM prompt cache hit rates" ([tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) minor-changes item 5). This is a genuinely useful primitive for jelly-fish's own `tools_hash`/tool-list-freeze machinery (agent-loop.md §5.5): the *spec's* cache hint and jelly-fish's *per-turn freeze* solve different problems (server-side TTL vs. same-turn consistency) and can stack without conflict — no redesign needed, just a note that a Connector's `ttlMs` is a hint for the client's between-turn cache, not something the loop needs to read.
- **Tool annotations**: `readOnlyHint` (default **false**), `destructiveHint` (default **true**, only meaningful when `readOnlyHint` is false), `idempotentHint` (default **false**, same caveat), `openWorldHint` (default **true**) ([schema, cited via research pass; defaults independently consistent with the tools spec's warning language](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#data-types)). The spec's own trust caveat, verbatim: **"For trust & safety and security, clients MUST consider tool annotations to be untrusted unless they come from trusted servers."** This is exactly the caveat ADR 0004 already assumes when it says hints merely "seed" the Approver's defaults rather than deciding outright — no conflict, just confirmation the ADR's caution is spec-mandated, not extra-cautious.
- **Structured output**: `outputSchema` (JSON Schema) plus a `structuredContent` field on the result (any JSON value); "a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block" for backward compatibility (same page). This maps cleanly onto provider-gateway.md's existing rule that "a structured JSON result is a `TextPart` holding the JSON" — jelly-fish's `msg.ToolResult.Parts` already gets this for free; `structuredContent` is additional metadata jelly-fish's MCP client can pass through as another content part, not something requiring a new `msg.Part.Kind`.
- **Content types**: `text`, `image`, `audio` (new since earlier revisions), `resource_link` (a URI pointer, not guaranteed to also appear in `resources/list`), and embedded `resource` blocks — all four+ support common `annotations` (`audience`, `priority`, `lastModified`) (same page). jelly-fish's `[]msg.Part` tool-result shape (provider-gateway.md §4.4) already accepts multi-part text+image; `audio` and `resource_link` are new kinds the Provider Gateway doesn't yet model — flagged as Q6.
- **Protocol error vs. `isError`**, exact spec framing: **Protocol Errors** ("unknown tool," malformed request, server error) are standard JSON-RPC errors "that models are less likely to be able to fix." **Tool Execution Errors** ("API failures," validation errors, business logic errors) are reported inside a normal result with `isError: true`, because they "contain actionable feedback that language models can use to self-correct and retry" (same page, "Error Handling"). This is already exactly jelly-fish's `tool.Result{IsError bool}` vs. a Go `error` split (agent-loop.md §4.2: "error = bug/infra; exec turns it into an is_error Result") — confirmed, no change needed.
- **Resources and prompts**: fully optional. A server that never declares `resources`/`prompts` capabilities is spec-valid; a client that never declares them in `clientCapabilities` is equally valid, and the server simply can't rely on what wasn't declared (server violating this returns `MissingRequiredClientCapabilityError`, `-32021`). product.md's "Later roadmap" deferral of resources/prompts is fine as written — no cross-spec issue here (contrast §9's Sampling/Roots finding, which *is* a conflict).
- **Stateful tools, non-normative guidance worth adopting anyway**: since MCP now has no protocol-level session, the spec's own suggested pattern for a Connector that needs cross-call state (a shopping cart, an open handle) is "return an explicit handle from a creation tool and accept that handle as an argument on subsequent calls" ([tools spec, "Stateful Tools"](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#stateful-tools)) — good context for anyone building jelly-fish's own eventual example Connectors, not something the client needs to implement.

## 6. Elicitation, sampling, roots — mapped onto `input_required`

### 6.1 The current mechanism: MRTR

- **How it fires**: any of `tools/call`, `resources/read`, `prompts/get` MAY return an `InputRequiredResult` instead of a normal result. Servers **MUST NOT** send it from any other request type ([MRTR spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)).
- **Exact shape** (verified directly against the spec page):
  ```json
  // tools/call (id: 2) response
  {
    "jsonrpc": "2.0", "id": 2,
    "result": {
      "resultType": "input_required",
      "inputRequests": {
        "github_login": {
          "method": "elicitation/create",
          "params": { "mode": "form", "message": "Please provide your GitHub username",
                      "requestedSchema": { "type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"] } }
        }
      },
      "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."
    }
  }
  ```
  ```json
  // tools/call retry (id: 3 — MUST differ from id: 2)
  {
    "jsonrpc": "2.0", "id": 3, "method": "tools/call",
    "params": {
      "name": "get_weather", "arguments": { "location": "New York" },
      "inputResponses": { "github_login": { "action": "accept", "content": { "name": "octocat" } } },
      "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."
    }
  }
  ```
- **`requestState` rules that matter for jelly-fish**: it is opaque — "Clients **MUST NOT** inspect, parse, modify, or make any assumptions about its contents" — and **MUST** be echoed back byte-for-byte on retry if present. If it influences authorization or business logic, the server itself must integrity-protect it (HMAC/AEAD) and check replay bounds (principal, TTL, originating-request digest) (same page, "Server Requirements"). This is entirely the *server's* problem, not jelly-fish's — jelly-fish's only obligation is to **store and echo it unmodified**.
- **No shared server-side state is required across the retry** — "This flow ... does not require a shared storage layer across server instances or requiring stateful load balancing" (same page). This is the exact property jelly-fish needs, since the session may park for days with no Worker and be resumed by a different Worker entirely.
- **A single `InputRequiredResult` can bundle several pending requests** (the `inputRequests` map, keyed by server-chosen strings), potentially mixing `elicitation/create`, `sampling/createMessage`, and `listRoots` requests in one round trip. Servers **MUST NOT** include a request type the client didn't declare in `clientCapabilities` — which is the clean mechanism for jelly-fish to *refuse* sampling and roots (§6.3): simply never declare those capabilities, and a spec-conformant server can't send them.

### 6.2 Mapping onto `input_required` / `elicitation.*`

- jelly-fish's own term **`input_required`** and the spec's own `resultType: "input_required"` are the same concept, not a coincidence worth losing — recommend keeping the name exactly.
- Recommended mapping, concretely:
  - MCP `InputRequiredResult{inputRequests, requestState}` on a `tools/call` → jelly-fish `elicitation.requested{connector, schema, request_state}`, parking `awaiting_user` (event-log.md §5.18 already has this shape, minus one field).
  - **⚠ cross-spec / must-fix**: event-log.md's catalog row for `elicitation.requested` currently lists only `{connector, schema}`. It needs a third field — an opaque `request_state` (store as an opaque string/blob, never parsed, never logged as secret-scrubbed-away since it isn't a secret but also isn't meaningful to anything but the Connector) — or the resume in §6.2 below cannot echo it back and a spec-conformant server will reject the retry. This is a small, mechanical addition, not a redesign.
  - User answers (via the reused approval UI, product.md) → `elicitation.resolved{answer}` → `runnable`.
  - **Resume, precisely**: the next Worker that claims the session re-issues `tools/call` with (a) the **original** tool arguments unchanged, (b) `inputResponses: {<same key the server used>: <ElicitResult>}`, (c) the stored `requestState` echoed verbatim. This *is* a new JSON-RPC request id at the wire level (the spec requires the id to differ) — but it is the same logical tool call at jelly-fish's abstraction level, so keeping the same `tool_call_id`/`idempotency_key` (as agent-loop.md's acceptance criteria already say) is correct; only the wire-level JSON-RPC id changes, and that id is the MCP client library's concern, not the Event Log's.
  - `ElicitResult.action` is one of `accept` (with `content` matching the schema)/`decline`/`cancel` — jelly-fish's `elicitation.resolved{answer}` payload should carry this three-way shape rather than collapsing it to a boolean, so a user's explicit "no" (decline) is distinguishable from "I closed the dialog" (cancel) — both are valid, common cases the Connector may want to handle differently ([elicitation spec, "Response Actions"](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)).
- **Form-mode schemas are deliberately tiny**: "flat objects with primitive properties only" — string/number/boolean/enum (single- or multi-select), with `format: email|uri|date|date-time` on strings ([elicitation spec, "Requested Schema"](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). This is good news for reusing the approval UI (product.md): one generic renderer for this restricted schema subset covers every Connector, no per-Connector custom form code needed.
- **URL mode** (introduced 2025-11-25, still current): the server sends a `url` instead of a schema; the client's only job is to show the user the destination and get consent before navigating, then retry with `{"action": "accept"}` (no `content`) — the *out-of-band* interaction (often a third-party OAuth flow the Connector itself needs, e.g. a GitHub Connector needing the user's own GitHub login) happens entirely outside the MCP session ([elicitation spec, "URL Mode"](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). This fits jelly-fish's parking model *better* than form mode: the "wait" is indefinite and externally-tracked, exactly like `awaiting_user` already assumes. Recommend supporting both modes from the base version — URL mode isn't extra client-side complexity, it's actually less (no schema-driven form to render, just a confirm-and-open dialog), and it's the spec's own answer to "Connector needs the user to log into some other service."
- The spec is explicit that URL-mode elicitation is **not** how the MCP client itself authorizes to the Connector (that's §7's OAuth flow) — it's for a *third-party* service the Connector talks to on the user's behalf, and "the third-party credentials **MUST NOT** transit through the MCP client" (same page, "Understanding the Distinction"). Good separation to preserve: jelly-fish's Connector-to-jelly-fish OAuth tokens (§7) and any third-party tokens a Connector manages for itself are different trust boundaries, and jelly-fish's client should never see the latter.

### 6.3 Legacy `elicitation/create` (the 5-minute hold) — and why it still matters

- **Confirmed**: prior to 2026-07-28 (protocol revisions 2025-06-18 through 2025-11-25), `elicitation/create` was a genuine **server-initiated JSON-RPC request**, sent over the live connection while the originating client request was still open — a synchronous round trip inside one call, not a retriable pattern. The spec text for that era does not mention any timeout or recovery behavior for a dropped connection mid-elicitation; it is silent (verified against the 2025-11-25 elicitation page structure; MRTR's changelog entry confirms this was "the previous approach of sending server-initiated requests" that MRTR explicitly replaces).
- **Unverified**: no primary source (MCP spec or changelog) states a specific "~5 minutes" number anywhere. jelly-fish's own agent-loop.md Decision 16/event-log.md §5.18 choice to hold the Worker "up to 5 minutes" for this legacy path is jelly-fish's **own** operational choice (an upper bound on how long a Worker can be tied up in-process), not something derived from the spec — this doc found nothing to contradict that number, but nothing to confirm it either. Recommend keeping it as jelly-fish's own tunable, documented as such rather than implied to be spec-derived.
- **Why this still matters in practice, not just for historical Connectors**: 2026-07-28 is brand new. Every product surveyed in §2 documents behavior against 2025-06-18/2025-11-25-era elicitation; none has publicly confirmed MRTR support yet. jelly-fish's Go SDK-based client needs the legacy in-process hold path for a long transitional period, likely measured in a year or more of ecosystem migration, not as a compatibility footnote. Recommend keeping Decision 16 exactly as designed, and treating MRTR support as the primary path with legacy as a real, load-bearing fallback rather than "rare edge case" in the implementation.

### 6.4 Sampling and Roots: refuse, cleanly

- **Both are now spec-deprecated** ("Deprecate the Roots, Sampling, and Logging features ... Suggested migrations: pass directories or files via tool parameters, resource URIs, or server configuration instead of Roots; integrate directly with LLM provider APIs instead of Sampling; log to `stderr` (stdio) or use OpenTelemetry instead of Logging" — [changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). They remain "fully functional during the deprecation window" (minimum twelve months) but "new implementations should not add support."
- **The refusal mechanism is already built into the spec**: a server "**MUST NOT** send an `inputRequests` that the client has not declared support for" (§6.1). jelly-fish's client simply never sets `sampling`/`roots` in `clientCapabilities` (or the legacy-era `capabilities` object); a conformant server can't ask, and a non-conformant one gets a capability-mismatch error the client already has to handle for any unsupported feature.
- **Sampling would have been redundant for jelly-fish anyway**: the whole point of Sampling is letting a Connector borrow the user's LLM connection for its own purposes. jelly-fish already owns that exact capability end-to-end via its Provider Gateway, BYOK keys, and Budget accounting (provider-gateway.md, ADR 0006) — wiring MCP Sampling would mean re-deriving usage/cost/budget accounting for a second, parallel LLM-call path the platform doesn't otherwise need. Recommend explicitly refusing it, permanently, not just "later roadmap."
- **Roots doesn't fit jelly-fish's model either**: Roots exists to tell a local server "here are the directories you may touch." jelly-fish already solves this differently — project files are indexed in the prompt and read via `read_upload` (context.md §5.2, provider-gateway.md Decision 23), and a stdio Connector's filesystem access is already bounded by running inside the Sandbox (ADR 0003) rather than by a client-advertised root list. Recommend refusing Roots too, and updating product.md's "Later roadmap" line (Q9).

## 7. Authorization (MCP spec + OAuth RFCs) and jelly-fish's design

### 7.1 Spec mechanics, verified against the current authorization page

- **Authorization is OPTIONAL overall**, and split by transport: "Implementations using an HTTP-based transport **SHOULD** conform to this specification. Implementations using an STDIO transport **SHOULD NOT** follow this specification, and instead retrieve credentials from the environment" ([authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). This is a direct, decisive answer to sandbox.md's Q10 — see §7.4.
- **Discovery flow**: MCP server 401s with `WWW-Authenticate: Bearer resource_metadata="https://.../.well-known/oauth-protected-resource"` → client GETs that Protected Resource Metadata (RFC 9728) document → extracts `authorization_servers` → discovers the AS via RFC 8414 (`/.well-known/oauth-authorization-server`) or OpenID Connect Discovery (client **MUST** support both discovery mechanisms) → proceeds to authorize (same page, plus [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.html), [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414.html)).
- **Client registration priority order** (spec-mandated): (1) pre-registered client info if the client already has it for this server, (2) **Client ID Metadata Documents** if the AS advertises `client_id_metadata_document_supported: true`, (3) **Dynamic Client Registration** (RFC 7591) as a fallback if the AS has a `registration_endpoint`, (4) prompt the user to enter client info manually ([client-registration spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). A CIMD document is a JSON file hosted at an HTTPS URL that *is* the `client_id`, containing at minimum `client_id`, `client_name`, `redirect_uris`; the AS fetches and validates it (`client_id` in the doc must match the URL exactly) on first use, no registration round trip. DCR remains "deprecated ... retained for backwards compatibility."
- **Resource parameter (RFC 8707) is mandatory, not optional**: "MCP clients **MUST** implement Resource Indicators for OAuth 2.0 ... The `resource` parameter: (1) MUST be included in both authorization requests and token requests. (2) MUST identify the MCP server ... (3) MUST use the canonical URI of the MCP server ... MCP clients **MUST** send this parameter regardless of whether authorization servers support it" (same authorization page). This is the mechanism that prevents one stolen/leaked token from being replayable against a different Connector.
- **PKCE**: required implicitly through the OAuth 2.1 base draft the spec adopts (OAuth 2.1 itself folds PKCE in as mandatory for all clients — [draft-ietf-oauth-v2-1-13](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13)); S256 code-challenge method, `code_verifier` 43–128 chars per [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html).
- **Token passthrough is explicitly banned**: "MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server. MCP servers **MUST** only accept tokens that are valid for use with their own resources. MCP servers **MUST NOT** accept or transit any other tokens" (authorization spec). This is a Connector-implementer's obligation, not jelly-fish's client's — but jelly-fish's client should never *try* to hand a Connector one of its own Provider Keys or another Connector's token, which it wouldn't anyway given jelly-fish's existing per-Connector credential model.
- **Refresh tokens**: clients that want them "**MUST** keep refresh tokens confidential in transit and storage," "**SHOULD** include `refresh_token`" in requested grant types, and "**MUST NOT** assume refresh tokens will be issued — the AS retains discretion" (authorization spec, "Refresh Tokens"). Servers should not require `offline_access` as a resource scope.
- **Scopes and step-up**: on `insufficient_scope`, the server responds `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="..."` (per [RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750.html)). The client is expected to re-authorize with **the union of previously granted scopes and the newly required ones** ("Determine required scopes by computing the union ... This ensures previously granted permissions are preserved"), then retry — "no more than a few times," treating repeated failure as permanent (authorization spec, "Step-Up Authorization Flow"). Servers must treat scopes as hierarchical (a broader scope implies narrower ones).
- **Mix-up/issuer-confusion defense (RFC 9207)**: the client must record the AS's `issuer` before redirecting, and validate a returned `iss` parameter against it before ever sending the authorization code to a token endpoint — this is now a MUST on the client side (authorization spec, "Authorization Response Validation").
- **Non-OAuth auth**: product.md already scopes this in — "custom URL and headers" alongside the OAuth "Connect" flow. This is exactly Claude Code's and Cursor's "static headers" mode and VS Code's "input variables" pattern (§2) — a user-supplied header name/value pair (or a bearer token pasted in directly), stored the same way as an OAuth token (§7.2), with no discovery/negotiation attempted.

### 7.2 Mapping onto jelly-fish's own architecture (not covered by the MCP spec — jelly-fish's own design questions)

- **Scope of "per user per Connector"**: CONTEXT.md scopes a Connector to a **Project**, and a Project belongs to one User (Workspace is reserved for a single user today). So concretely this is "one OAuth grant per (Project, Connector)" today, which happens to equal "per user per Connector" until Workspaces gain more than one User. Recommend keying storage by `(project_id, connector_id)` now so it doesn't need reshaping later, with a note that multi-user Workspaces would need a decision on whether a Connector's grant is shared per-Workspace or re-authorized per-User (not a base-version problem).
- **The redirect flow itself**: since jelly-fish is a server (Go `api` role) + PWA, not a native app, the natural shape is: PWA hits an API route ("Connect this Connector") → API (acting as the OAuth client, holding or generating the CIMD document / DCR registration) builds the authorization URL with PKCE + `resource` + recorded `issuer`, and redirects the user's browser to the AS → AS redirects back to an API callback route → API exchanges the code for tokens (server-side, PKCE verifier never leaves the API) → tokens stored encrypted (below) → PWA is told "connected." This keeps the flow entirely inside jelly-fish's own trust boundary (the browser never sees a token), matching how product.md already treats Provider Keys.
- **Token storage**: recommend the exact same pattern product.md already commits to for Provider Keys — **envelope-encrypted, decrypted only in the Worker** (since ADR 0003 says remote Connectors are called from the Worker over HTTP, that's the only place the plaintext token is ever needed) — in a dedicated table, never in the Event Log (event-log.md's payload rule "Secrets never enter payloads" already generalizes to this). Store access token, refresh token (if any), scopes granted, and the AS `issuer` it's bound to — the spec explicitly requires credentials be "keyed by the authorization server's `issuer` identifier" and never reused across a changed AS (client-registration spec, "Authorization Server Binding").
- **⚠ jelly-fish design gap, not in any doc today: refresh races across Workers.** Two Workers, each driving a different session in the same Project, may both see the same Connector's access token expired at roughly the same moment and both attempt a refresh concurrently. Standard OAuth refresh can invalidate the old refresh token on rotation, so a naive "read token, if expired refresh, use it" risks one Worker's refresh invalidating the token the other Worker just received. Recommend reusing jelly-fish's own fencing pattern (event-log.md §5.1/§5.2's lease/fencing) at a smaller scale: a `SELECT ... FOR UPDATE` on the credential row before refreshing, refresh-and-write in the same transaction, so a second concurrent Worker blocks on the row lock and then re-reads the just-refreshed token instead of double-refreshing. This needs no new infrastructure, just the same technique already used elsewhere in the codebase.
- **Revocation**: when a user disconnects a Connector, delete the stored encrypted credential row immediately (that's the primary control); calling the AS's own revocation endpoint (a standard, if not MCP-specific, OAuth capability — **Unverified** whether the MCP spec itself requires clients to support it) is a reasonable courtesy best-effort call, not something to block the "disconnect" UX on.
- **Recommended error class**: when a Connector call returns 401 mid-turn, jelly-fish should treat it the way provider-gateway.md already treats a Provider key going bad — a new terminal class (e.g. `connector_auth_required`) that parks `awaiting_user` with a "Reconnect `<Connector>`" action reusing the same OAuth flow, rather than surfacing it as a generic tool error the model has to puzzle over.
- **SSRF, a jelly-fish-specific gap this research surfaces**: product.md lets a non-technical user paste an arbitrary Connector URL, and per ADR 0003 remote Connectors are called **from the Worker, over HTTP** — meaning the Worker process itself (not the Sandbox) is the one issuing outbound requests to a user-supplied URL, both for the MCP calls and for OAuth discovery (Protected Resource/Authorization Server Metadata fetches). This is a *different* attack surface than the Sandbox egress question sandbox.md already discusses (§10 there) — that's about code running inside a container; this is about the platform's own Worker process. The MCP security best-practices page confirms this is exactly the scenario it's warning about: "attackers can induce an MCP client to make HTTP requests to unintended destinations during OAuth metadata discovery," citing internal IPs, `169.254.169.254`, localhost services, and DNS rebinding as concrete vectors, with mitigations "Enforce HTTPS... Block Private IP Ranges... Validate Redirect Targets... Use Egress Proxies... pin DNS resolution results between check and use" ([security best practices §SSRF](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#server-side-request-forgery-ssrf)). This needs its own decision in whatever spec eventually covers Connector setup — flagged as Q10.

### 7.3 Comparison: DCR vs CIMD

| | Dynamic Client Registration (RFC 7591) | Client ID Metadata Documents (CIMD, draft) |
|---|---|---|
| MCP status (2026-07-28) | Deprecated, fallback only | **SHOULD** support, preferred |
| Mechanism | Client POSTs metadata to the AS's `registration_endpoint`, gets back `client_id`(+secret) | Client hosts a JSON doc at an HTTPS URL; that URL **is** the `client_id`; the AS fetches it on demand |
| Registration step needed? | Yes, one-time per AS | No — self-describing, fetched lazily |
| Portable across a changed AS? | No — credentials are bound to the AS that issued them, must re-register on change | Yes — the URL-based `client_id` needs no re-registration when the AS changes |
| Where jelly-fish's client fits | Fallback when an AS doesn't support CIMD (still common in late 2025/2026) | Primary path: jelly-fish hosts one client-metadata JSON per environment, used for every Connector's AS |

### 7.4 Resolving sandbox.md's open questions

- **sandbox.md Q10 (do Connector secrets ever need to enter the Sandbox?) — yes, and the spec says so directly.** For local stdio Connectors, MCP's own authorization spec says implementations "**SHOULD NOT** follow this specification, and instead retrieve credentials from the environment" (§7.1). Concretely: if a local stdio Connector itself needs an API key (e.g. a "weather" Connector wrapping a paid weather API), that credential is expected to arrive as a process environment variable, exactly the `OPENHANDS_SECRET_*`-style pattern sandbox.md's §13 already flagged as "a real precedent... but jelly-fish has no documented answer either way." Recommend: yes, inject such secrets as environment variables into the Sandbox process at `Sandbox.Exec` time for that one Connector's process, scoped as narrowly as possible (never written to the Workspace Volume, never logged — same secret-scrubbing invariant event-log.md already has for tool args).
- **sandbox.md Q8 (stdio Connector process supervision across a Worker crash) — the spec's own posture supports the simpler option.** The stdio transport section's guidance — "client SHOULD restart it... in-flight requests are lost; client retries against fresh process" — describes exactly jelly-fish's existing "never auto-retry a tool call, respawn clean" posture (event-log.md §5.5/§6: an unmatched `tool.call.started` becomes `tool.call.interrupted`, never re-run). Recommend option (i) from sandbox.md's own list: the Worker starts the stdio Connector process via `Sandbox.Exec` and holds the pipe itself; on Worker crash, the process dies with the container exec (or is cleaned up on next claim), the pending call becomes `tool.call.interrupted` like any other tool, and whichever Worker claims the session next simply spins up a fresh stdio process for that Connector on its next call. No in-container supervisor daemon is needed for the base version — the "no protocol-level session" architecture of 2026-07-28 was explicitly designed not to require one.

## 8. Security

- **Tool poisoning / prompt injection via descriptions**: first named by Invariant Labs (2025-04-01), demonstrating a Cursor-targeted attack where hidden `<IMPORTANT>` instructions in a tool description told the model to exfiltrate SSH keys while narrating something innocuous ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks), secondary vendor source; the pattern itself — tool descriptions being untrusted, model-visible input — is exactly why jelly-fish's ToolDef annotations are only *hints* per §5, and is the same class of risk as the "must show tool inputs to the user before calling" line already in the tools spec's Security Considerations, §5).
- **Rug-pull (definition change after approval)**: an MCP server silently changes a tool's description/behavior after a user approved it once; MCP hosts historically "bind trust to the tool's name, not its actual content" ([practical-devsecops glossary](https://www.practical-devsecops.com/glossary/rug-pull-attack-in-mcp/), secondary; tracked as CVE-2025-54136). The spec's own `listChanged` mechanism only tells a client to re-fetch the list — it does not mandate re-approval (`notifications/tools/list_changed`, §5). ⚠ cross-spec: jelly-fish's agent-loop.md Decision 4 already freezes the tool list per turn and hashes it (`tools_hash`), which limits *mid-turn* surprise, but says nothing about re-approval when a Connector's tool changes shape between turns. Recommend: when a previously-approved tool's schema or annotations change between turns (detectable via a content hash of name+description+schema, stored alongside the existing Approval Rule), treat it as a new tool for approval purposes rather than silently reusing the old rule — flagged as Q8.
- **Confused deputy**: MCP's own spec describes the canonical case precisely — a proxy MCP server with a static client_id to a third-party AS, plus per-MCP-client DCR, plus a stale AS consent cookie in the user's browser, lets an attacker's crafted redirect steal an authorization code without a fresh consent screen ([security best practices §confused deputy](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#confused-deputy-problem)). Not directly applicable to jelly-fish unless jelly-fish itself ever acts as a *proxy* MCP server fronting other AS's for its users (it doesn't in the base version — jelly-fish is only a client) — worth remembering if a "jelly-fish as MCP server" feature is ever added.
- **Token passthrough**: covered in §7.1; it's a Connector-author obligation. jelly-fish should just never do the client-side equivalent — handing a Connector a token that wasn't minted for it (its own credential model already prevents this by construction, since tokens are stored per-Connector, per §7.2).
- **SSRF**: covered in depth in §7.2 (Worker-side, distinct from Sandbox egress in sandbox.md). MCP's spec-listed mitigations — block RFC 1918/loopback/link-local ranges including `169.254.169.254`, enforce HTTPS in production, validate redirect targets, consider an egress proxy, pin DNS between check-and-use — apply directly to whatever HTTP client the Worker uses for Connector calls and for OAuth discovery fetches (security best practices, same page as above).
- **Secret scrubbing**: no MCP-specific spec text beyond the general injunction to keep tokens confidential; OWASP's guidance is the usable primary-adjacent source — never log secrets in plaintext, mask/redact rather than omit-and-hope, apply detection at each stage of the secret lifecycle ([OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). jelly-fish already has this invariant for tool args and Provider Keys (event-log.md payload rules); recommend the same "scrub known secret header names" pass explicitly covers `Authorization: Bearer ...` and any custom static-header credentials configured for a Connector (§7.1's non-OAuth path), not just Provider Keys.
- **OWASP MCP Top 10** exists as a living, Phase-3-beta community framework (10 named categories, e.g. Token Mismanagement, Privilege Escalation via Scope Creep, Tool Poisoning, Shadow MCP Servers — [owasp.org/www-project-mcp-top-10](https://owasp.org/www-project-mcp-top-10/)); useful as a checklist when this feature reaches implementation, but it is a community project, not a standards body — treat its rankings as directional, not authoritative.

## 9. Scaling: tools per Connector, namespacing, deferred loading

- **No vendor publishes a "too many tools" number.** The closest primary-adjacent data point: each MCP tool definition costs roughly 550–1,400 tokens of prompt space once expanded (name, description, JSON schema); one observed real-world case burned 143k of a 200k context window on schemas from just 3 servers ([apideck, secondary](https://www.apideck.com/blog/mcp-server-eating-context-window-cli-alternative)). Given product.md's own framing ("a small catalog of popular connectors, plus 'add custom'" for a friends-scale, non-technical audience), jelly-fish's base version is unlikely to hit this ceiling — recommend not building deferred/searchable tool loading for the base version, but treating it as the known answer once/if the Connector catalog grows (Claude Code's `tool_search` precedent, §2, is the pattern to copy then, and its own numbers — ~90k→~15k tokens for 147 tools — are the concrete case for when it's worth it).
- **Namespacing**: the spec itself now recommends prefixing on collision (§2/§5), and no client implements it automatically — it's manual, developer-side convention everywhere surveyed. Recommend a simple, explicit rule for jelly-fish: when two Connectors attached to the same Project expose a tool with the same name, prefix both with the Connector's own stable id (not its human-readable `name`, which the spec explicitly says "is not guaranteed to be unique... and SHOULD NOT be relied upon for disambiguation") — e.g. `<connector_id>__<tool_name>`, matching agent-loop.md's `ToolDef.Source` field (`"connector:<id>"`) which already carries exactly this identifier.
- **`tools_hash`/cache interplay**: covered in §5 — the new `ttlMs`/`cacheScope` fields are a server-side cache hint layered underneath jelly-fish's own per-turn freeze, not a replacement for it.

## 10. Open questions for grilling

1. **Should jelly-fish's base version support MRTR-only, or must it also implement the full legacy (pre-2026-07-28) `initialize`-handshake + server-initiated-request path from day one?** Proposed: implement both from day one — real-world Connectors will be split across both eras for a long transition period (§6.3), and agent-loop.md's Decision 16 already designed for exactly this split.
2. **What's the exact `elicitation.requested` payload addition needed for `requestState`?** Proposed: add `request_state` (opaque string, unbounded-ish size within the existing 32KB inline/blob threshold) to the event-log.md §4 catalog row, echoed byte-for-byte on `elicitation.resolved`'s resume — a one-line addition to that spec (§6.2).
3. **Does `elicitation.resolved{answer}` need to carry the three-way `accept`/`decline`/`cancel` action, not a boolean?** Proposed: yes — a Connector may want different behavior for an explicit decline vs. a dismissed dialog, and the spec models these as distinct outcomes (§6.2).
4. **Does jelly-fish support URL-mode elicitation in the base version, or form-mode only?** Proposed: support both — URL mode is *less* client-side work (no schema-driven form), fits the existing `awaiting_user` park model perfectly, and is the spec's own answer to "Connector needs the user to authorize a third-party service" (§6.2).
5. **Should Sampling and Roots ever appear on jelly-fish's roadmap?** Proposed: no — both are now spec-deprecated, and jelly-fish already has an equivalent to each (Provider Gateway for Sampling, project-files-in-prompt + Sandbox scoping for Roots). Recommend editing product.md's "Later roadmap" line to drop "sampling" (and not add "roots") — flagged as a conflict to fix, not a decision this doc makes unilaterally (§6.4).
6. **Does jelly-fish's `msg.Part` need new `Kind`s for MCP's `audio` and `resource_link` content types?** Proposed: `audio` — add a new `Kind` when a Connector that returns audio is actually built (additive, no `msg_v` bump per ADR 0002's existing rule); `resource_link` — likely fine represented as a `TextPart` with the URI, deferred until resources are supported at all (§5).
7. **How exactly does jelly-fish key OAuth-connector credential storage — by `(project_id, connector_id)`, `(user_id, connector_id)`, or both?** Proposed: `(project_id, connector_id)` for the base version, with the AS `issuer` stored and checked (spec MUST: credentials are bound to the issuer, re-register if it changes), matching CONTEXT.md's Connector-is-project-scoped definition; revisit only if/when Workspaces gain more than one User (§7.2).
8. **Should a Connector tool's approval "stick" across a spec-visible definition change (rug-pull), or only across an unchanged hash?** Proposed: hash the tool's name+description+schema (+annotations) at approval time; on any Approval Rule use, compare the hash and require re-approval on mismatch, surfaced to the user as "this tool's definition changed since you approved it" (§8).
9. **Who owns the Worker-side SSRF mitigation (blocking internal IPs / `169.254.169.254` / DNS-rebinding) for arbitrary user-supplied Connector URLs — this feature's spec, or a shared "outbound HTTP from the platform" concern used by both this and future features?** Proposed: specify it here, since Connector URLs are the only place today a non-technical user directly supplies an arbitrary remote endpoint the Worker will call; revisit as a shared concern only if another feature needs the same protection later (§7.2, §8).
10. **Token refresh races across Workers — is a `SELECT ... FOR UPDATE` fencing pattern on the credential row sufficient, or does this need the same `lease_epoch` fencing machinery event-log.md uses for sessions?** Proposed: the simpler row lock is sufficient — this is a much smaller/shorter-lived critical section than a session Lease, and doesn't need a renewable, heartbeat-based lease of its own (§7.2).
