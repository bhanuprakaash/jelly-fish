# Sandbox: Research

Status: research, 2026-09-27. Terms follow [`CONTEXT.md`](../../CONTEXT.md): the isolated container attached to a session is the **Sandbox** (never "computer", "VM", "box", "remote", "environment"); a session with one attached is a **Sandboxed Session** (never "remote session"); `/remote` only attaches a Sandbox, it does not start one. Facts cite primary sources inline. **Unverified** marks anything not confirmed from a primary source (official docs, source code, or a spec/RFC). "⚠ cross-spec" flags a conflict or gap against an existing ADR/design doc; it is flagged here, not resolved — resolution is a decision for the spec.

> Ground truth, not redesigned here: ADR [0003](../adr/0003-nothing-executes-on-the-host.md) (nothing executes on the host; Sandboxes are lazy, Docker now, Kubernetes pods later), ADR [0004](../adr/0004-layered-approver-no-implicit-rules.md) (sandbox actions are free under the Approver — "the container limits the blast radius"), ADR [0006](../adr/0006-byok-llm-platform-metered-services.md) (sandbox compute is a metered Platform Service), [product.md](../product.md) (`Sandbox` interface: create, exec, stream, files, stop, resume; one default image; CPU/memory/wall-clock caps; open egress in the base version; Quotas; hard delete), [agent-loop.md](../design/agent-loop.md) (`CallInput.Sandbox sandbox.Handle`, Decision 11 tool timeout and process-group kill, Interrupt via ctx cancel), [event-log.md](../design/event-log.md) (`sandbox.requested/.started/.stopped/.failed` events, waiting states hold no Sandbox, `usage.recorded`, hard delete), [provider-gateway.md](../design/provider-gateway.md) (`save_artifact(path)` copies a file out of the Sandbox; `read_upload`; project files are an index in the prompt, read via a tool, Decision 23), [TODO.md](../../TODO.md) ("Sandbox" and "Uploads and artifacts" items).

## 1. Summary

- Docker's own `exec` API cannot be killed or given a timeout ([moby#35703](https://github.com/moby/moby/issues/35703)); the Sandbox must run every command in its own process group (via `setsid`) and, on timeout or Interrupt, send `TERM` to the group, wait a grace period, then `KILL` — this is already assumed by [agent-loop.md](../design/agent-loop.md) Decision 11 and sketched in [research/agent-loop.md §7.3](agent-loop.md), but the grace period isn't fixed yet (§4, Q1).
- Every serious multi-tenant sandbox product surveyed (E2B, Modal, Codex cloud, Kata, gVisor's own docs) treats plain Docker/runc as **not** a security boundary for untrusted code, because containers share the host kernel ([gVisor](https://gvisor.dev/blog/2019/11/18/gvisor-security-basics-part-1/), recent runc CVEs). This sits in tension with ADR 0004's "the container limits the blast radius" — flagged in §5.
- Whether project files live inside the Sandbox filesystem (e.g. `/project/…`) is still open (TODO.md flags this from provider-gateway grilling); [provider-gateway.md](../design/provider-gateway.md) Decision 23 only puts an *index* in the prompt, read via `read_upload`, which doesn't help a shell command that needs the actual files on disk (§6).
- The `Sandbox` interface (product.md: create, exec, stream, files, stop, resume) has no fixed shape yet. §7 proposes one consistent with `CallInput.Sandbox sandbox.Handle` (agent-loop.md) and the streaming/blob conventions already fixed elsewhere (event-log.md, context.md).
- ⚠ cross-spec: the `sessions` table (event-log.md §3) has no column for "which container belongs to this session," yet a Worker recovering from a crash must find it. §8 proposes deterministic naming (a Docker label keyed on session id) instead of a new column.
- Recommendation (§14): keep ADR 0003's "Docker now," but run it under gVisor's `runsc` runtime rather than plain `runc`, given every primary source on multi-tenant untrusted code says plain containers are insufficient. This is a `--runtime` flag, not a new abstraction — cheap to adopt within "Docker now," and Kata/Firecracker stay available for the Kubernetes-backend roadmap item.

## 2. Where the Sandbox sits (ground truth recap)

- ADR 0003: "No tool ever touches the worker's or server's filesystem or processes. Shell, file tools, and local (stdio) Connectors run only inside the session's Sandbox, reached through a `Sandbox` interface (Docker now, Kubernetes pods later)." Attached lazily: project default, agent request (behind an approval), or `/remote`. Idle Sandboxes are stopped; the Workspace Volume persists 7 days.
- ADR 0004: inside the Sandbox, actions are free under the Approver, "since the container limits the blast radius." External tools are still gated.
- product.md §Sandbox: `Sandbox` interface (create, exec, stream, files, stop, resume); Docker implementation first; nothing ever runs on the host; created only when needed; one default image (Python, Node, Go, git, common CLIs); stopped when idle, Workspace Volume persists and deletes after 7 days idle; CPU, memory and wall-clock caps; **open network egress** in the base version. Usage dashboard shows sandbox compute as CPU-s, GB-s, disk, egress. Admin Quotas: concurrent sandboxes, compute hours, storage. Roadmap (later): Kubernetes sandbox backend, custom images per project, an egress allowlist.
- agent-loop.md: `CallInput{CallID, IdempotencyKey, Args, Sandbox sandbox.Handle}` — every `Tool.Call` gets a handle, not just the shell tool. Decision 11: tool timeout 120s default, shell defaults to the Sandbox wall-clock cap, `ToolDef.Timeout` overrides; "on timeout the Sandbox kills the process group itself (Docker can't kill an exec, moby#35703): TERM, grace, KILL." Interrupt (§5.4/§5.8): `ctx` cancellation must reach "Sandbox exec kills the process in the container" (event-log.md §5.8 step 3).
- event-log.md: event catalog has `sandbox.requested` / `.started` / `.stopped` / `.failed` {sandbox_id, image, reason}, Worker-fenced. Waiting states table: `awaiting_approval` holds no Worker and no Sandbox ("Sandbox stopped when idle"); every `awaiting_*`/`sleeping` status holds no Sandbox. Hard delete's async cleanup job deletes "the Sandbox and Workspace Volume" by session prefix.
- provider-gateway.md: `save_artifact(name, content?, path?)` (TODO.md, not yet a full spec) takes a Sandbox container path and copies it out as an Artifact. `read_upload(id, pages?)` also "reads project files" (Decision 23) but only returns content into the prompt — it does not place a file inside the Sandbox.
- research/agent-loop.md §7.3 (background, not a decision): "`Sandbox.Exec` must start commands in their own process group and record the PID, then on `ctx.Done()` run a second exec: `kill -TERM -<pgid>`, wait for a grace period, then `-KILL`." No grace-period number is given.

## 3. Prior art survey

### 3.1 Cloud sandbox products (agent code-execution as a service)

**E2B** (e2b.dev) — one Firecracker microVM per sandbox, in its own cgroup and network namespace, with a per-sandbox nftables egress firewall; E2B builds a custom minimal kernel to shrink attack surface ([e2b-dev/firecracker](https://github.com/e2b-dev/firecracker), [firecracker-vs-qemu](https://e2b.dev/blog/firecracker-vs-qemu), [customize-sandbox-compute](https://e2b.dev/blog/customize-sandbox-compute)). Lifecycle: create, pause (retains filesystem/memory state indefinitely), resume, `on_timeout` = `"kill"` (default) or `"pause"`, max timeout 24h Pro / 1h Hobby ([sandbox](https://docs.e2b.dev/sandbox), [timeouts](https://e2b.dev/docs/legacy/sandbox/api/timeouts)). `exec`/`run` stream stdout/stderr via callbacks, default command timeout 60s, kill by PID (`sandbox.commands.kill(pid)`), list processes ([streaming](https://e2b.dev/docs/code-interpreting/streaming)). Egress: on by default, `allowInternetAccess=false` disables it; otherwise IP/CIDR and domain allow/deny lists, allow taking precedence, DNS auto-allowed to 8.8.8.8 ([internet-access](https://docs.e2b.dev/network/internet-access)). Billed per-second for CPU/RAM while running, stops on pause/kill/timeout ([billing](https://e2b.dev/docs/billing)). **Unverified**: exact process-group/PID-namespace mechanics for killing an individual command (vs. killing the whole microVM); no explicit statement on blocking `169.254.169.254`.

**Modal sandboxes** (modal.com) — isolation is **gVisor** ([sandbox-networking](https://modal.com/docs/guide/sandbox-networking), [gvisor](https://github.com/google/gvisor)). Five lifecycle states: Created → Scheduled → Started → Ready (optional probe) → Finished; default timeout 5 min, up to 24h; idle timeout auto-terminates; `sandbox.terminate()` ([sandbox](https://modal.com/docs/guide/sandbox), [modal.Sandbox](https://modal.com/docs/reference/modal.Sandbox)). `exec()` returns a `ContainerProcess` with stdin/stdout/stderr streams, PTY mode, blocking or streaming reads ([sandbox-spawn](https://modal.com/docs/guide/sandbox-spawn)). File API: `read_text/write_bytes/read_bytes/write_text/list_files/stat/make_directory/copy_from_local/copy_to_local/watch`, plus `snapshot_filesystem()` for reusable images ([modal.Sandbox](https://modal.com/docs/reference/modal.Sandbox)). Resource limits: fractional CPU cores, memory in MiB, both with optional hard `(request, limit)` pairs; disk billed at 20:1 against memory ([resources](https://modal.com/docs/guide/resources)). Networking: secure-by-default (no inbound, no workspace-resource access); outbound restrictable via `block_network=True`, `outbound_cidr_allowlist`, or `outbound_domain_allowlist` (TLS SNI, beta) ([sandbox-networking](https://modal.com/docs/guide/sandbox-networking)). Timeout sends SIGKILL, exit code 137. **Unverified**: whether a SIGTERM grace period precedes the SIGKILL.

**Daytona** (daytona.io) — Docker/OCI containers, **not** gVisor, "complete isolation" (dedicated kernel claim is marketing language, not confirmed at the syscall level); 90ms cold start ([docs](https://www.daytona.io/docs), [daytonaio/daytona](https://github.com/daytonaio/daytona)). Create/start/stop/resume/snapshot lifecycle. **Note**: as of the public repo, Daytona's production codebase went closed-source and the public repo is frozen (AGPL-3.0, no further updates) — reduces its value as prior art for a self-hosted design. **Unverified**: networking controls, timeout/kill signal sequence (a PR discusses bounded output on timeout but not the signal mechanics, [PR #5145](https://github.com/daytonaio/daytona/pull/5145)).

### 3.2 Coding-agent sandboxes (local or hosted, tied to one agent)

**OpenAI Codex** — cloud tasks run in containers with no host filesystem/network access by default, optional internet access per task ([codex/overview](https://platform.openai.com/docs/codex/overview)); exact container isolation tech for the cloud service is **Unverified** (not documented). The Codex **CLI** uses platform sandbox backends: Linux/macOS use `bubblewrap` (`bwrap`) with `--unshare-pid`, seccomp network filtering, `PR_SET_NO_PRIVS`, and a read-only root (`--ro-bind / /`) with specific writable paths added via `--add-dir` ([linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md), [issue #27943](https://github.com/openai/codex/issues/27943)). **Unverified**: exact SIGTERM/SIGKILL timing (issues report cleanup problems, [#24933](https://github.com/openai/codex/issues/24933), but no documented grace period).

**Claude Code sandboxing** — macOS (built-in) and Linux/WSL2 (needs `bubblewrap` + `socat`) ([sandboxing](https://code.claude.com/docs/en/sandboxing)). Backed by the **sandbox-runtime** research-preview project ([anthropic-experimental/sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)): macOS uses `sandbox-exec` with a dynamically generated Seatbelt profile (written to a 0600 temp file, stale ones >5 min swept to avoid `ARG_MAX` overflow, [PR #303](https://github.com/anthropics/sandbox-runtime/pull/303)); Linux uses `bubblewrap` with nested PID-namespace isolation and a seccomp filter that blocks `AF_UNIX` socket creation; Windows runs commands as a dedicated `srt-sandbox` account with Windows Filtering Platform egress rules. Filed issues confirm it currently does **not** send SIGTERM before SIGKILL ([#62987](https://github.com/anthropics/claude-code/issues/62987)) and that a killed-by-signal wrapped process exits status 0, masking the kill ([sandbox-runtime#602](https://github.com/anthropics/sandbox-runtime/issues/602)). Network is proxied (HTTP proxy / SOCKS5 / Unix domain socket on Linux).

**OpenHands runtime** (All Hands AI, formerly OpenDevin) — one Docker container per session, an in-container "action execution server" receives actions over a REST API ([architecture/runtime](https://docs.openhands.dev/modules/usage/architecture/runtime)). Commands run under `tmux` (for persistent bash) or `subprocess.Popen`. Timeout handling **does** do TERM→KILL on the whole process group: `os.killpg(pgid, signal.SIGTERM)`, grace period, then SIGKILL fallback — but subprocesses detached with `nohup`/`setsid`/`disown`/`&` can still escape and outlive the task, tracked as an open issue ([#17732](https://github.com/All-Hands-AI/OpenHands/issues/17732)). Workspace persistence: bind mount, named volume, or overlay (copy-on-write) — `host_path:container_path[:mode]`. MCP tools are exposed via FastMCP inside the runtime for the tools OpenHands itself ships (e.g. git), with secrets injected as `OPENHANDS_SECRET_*` env vars.

### 3.3 Isolation technology (primary sources)

- **Plain Docker/runc**: Docker's own docs concede the point directly — "the default set of capabilities and mounts given to a container may provide incomplete isolation, either independently, or when used in combination with kernel vulnerabilities" ([engine/security](https://docs.docker.com/engine/security/)). Recent concrete evidence: **CVE-2025-31133**, **CVE-2025-52565**, **CVE-2025-52881** — runc symlink/mount races that let a container write host `procfs` files and escape ([CNCF writeup](https://www.cncf.io/blog/2025/11/28/runc-container-breakout-vulnerabilities-a-technical-overview/); secondary summary of the CVEs, treat the CVE identifiers as the primary fact and the writeup's framing as secondary).
- **gVisor** (`runsc`) — a user-space application kernel implemented in memory-safe Go; intercepts *every* application syscall in its "Sentry" component, so "no syscall is passed through directly to the host" and only ~68 host syscalls are ever reached (vs. 350+ for a native kernel) ([architecture_guide/intro](https://gvisor.dev/docs/architecture_guide/intro/), [architecture_guide/security](https://gvisor.dev/docs/architecture_guide/security/)). gVisor's own security post states plainly: "containers are not a sandbox… using them to run untrusted or potentially malicious code without additional isolation is not a good idea," because "container escape is possible with a single vulnerability" in the shared kernel ([gvisor-security-basics-part-1](https://gvisor.dev/blog/2019/11/18/gvisor-security-basics-part-1/)). Cost: per-syscall overhead, best for I/O-light workloads, integrates as a Docker/Kubernetes OCI runtime (`--runtime=runsc`) with no change to the container API surface.
- **Firecracker** — a VMM using Linux KVM to run microVMs, combining "the security and workload isolation properties of traditional VMs with the speed, agility and resource efficiency… of containers" ([design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)); ~125ms boot, <5 MiB overhead per VM. A companion **jailer** process sets up cgroups/chroot with elevated privilege, then drops privilege before executing the (unprivileged) Firecracker binary, which can then only access explicitly granted resources. Powers AWS Lambda/Fargate; AWS states tenant isolation means "execution environments never share or reuse virtual resources… across functions" and every function can be wrapped in "a virtual machine barrier" ([lambda tenant-isolation](https://docs.aws.amazon.com/lambda/latest/dg/tenant-isolation.html)).
- **Kata Containers** — OCI-compatible runtime that runs each container inside a lightweight VM via KVM, using Cloud Hypervisor (default), Firecracker, or QEMU as the backend hypervisor ([katacontainers.io](https://katacontainers.io/), [docs](https://katacontainers.io/docs/)). Hardware-enforced isolation, higher cold-start cost than gVisor, near-zero steady-state overhead for syscall-heavy workloads (**Unverified**/secondary comparison: [northflank blog](https://northflank.com/blog/kata-containers-vs-gvisor)).
- **Kubernetes `agent-sandbox`** — a real SIG Apps project exists: [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox). It defines a `Sandbox` CRD and controller for a single, stateful, singleton pod with a stable identity and persistent storage, aimed at AI agents and untrusted-code workloads; it deliberately **delegates isolation to a `RuntimeClass`** (gVisor or Kata), rather than inventing its own — i.e. it's an orchestration layer, not an isolation mechanism itself. Directly relevant to product.md's "Kubernetes sandbox backend" roadmap item.
- **moby/moby#35703**: the core complaint is that Docker's `exec` has no `stop`/`kill` endpoint the way a container does — "one can't kill such a process" ([issue](https://github.com/moby/moby/issues/35703)); the proposed (never shipped) fix was `/exec/{id}/stop` and `/exec/{id}/kill` API endpoints. Root cause: a process running as PID 1 (or effectively unreachable by signal from outside its own tree) ignores default-disposition signals unless it installs its own handler — standard PID-1/namespace signal semantics ([pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)). Community workarounds converge on the same set: (a) an init process as PID 1 — **tini**, which forwards signals and reaps zombies, has a `-g` flag to signal the whole process group ([krallin/tini](https://github.com/krallin/tini)); or **dumb-init**, which by default runs the child in its own session and proxies signals to that session (`DUMB_INIT_SETSID=0` for single-process mode) ([Yelp/dumb-init](https://github.com/Yelp/dumb-init)); (b) run the exec'd command under `setsid` so it heads its own process group, then signal the *group* with `kill(-pgid, sig)` — POSIX: "if pid is negative, but not -1, sig shall be sent to all processes… whose process group ID is equal to the absolute value of pid" ([kill(3p)](https://pubs.opengroup.org/onlinepubs/009695399/functions/kill.html), [setsid(2)](https://man7.org/linux/man-pages/man2/setsid.2.html)). This is exactly the mechanism research/agent-loop.md §7.3 already sketches.
- Docker's own timeout precedent: `docker stop` sends SIGTERM, waits a default grace period (**10s Linux / 30s Windows**), then SIGKILL; configurable via `--timeout`/`--stop-timeout`, `-1` disables it ([docker container stop](https://docs.docker.com/reference/cli/docker/container/stop/)). This is a reasonable anchor for the Sandbox's own TERM→grace→KILL number (§4).

## 4. Timeout kill of the process group (must-cover #1)

- **The problem** (confirmed, §3.3): a `docker exec`'d process cannot be killed or timed out through the Docker API itself ([moby#35703](https://github.com/moby/moby/issues/35703)). Closing the attach stream does not stop it.
- **The mechanism already assumed** by agent-loop.md Decision 11 and sketched in research/agent-loop.md §7.3: `Sandbox.Exec` starts the command under `setsid` (own process group, PID = PGID), records the PGID, and on timeout or `ctx.Done()` runs a *second* `docker exec` in the same container: `kill -TERM -<pgid>`, wait a grace period, `kill -KILL -<pgid>`.
- **PID 1 matters too**: the container's own entrypoint should be a minimal init (`tini` or `dumb-init`) so the container reaps zombies from any process the setsid'd command spawns and forgets to wait() on ([tini](https://github.com/krallin/tini), [dumb-init](https://github.com/Yelp/dumb-init)); this is orthogonal to the per-exec kill (it protects PID exhaustion across the container's lifetime, not any single command).
- **Grace period**: no primary source gives one specific number for an agent sandbox. Docker's own default for `docker stop` is 10s on Linux ([docs](https://docs.docker.com/reference/cli/docker/container/stop/)); OpenHands' equivalent kill path (the closest working precedent, §3.2) doesn't document its number either (**Unverified**). Proposal (§14 Q1): 5s grace, tunable, shorter than Docker's container-level default because this is an in-flight *command* the user is actively waiting on, not a container teardown.
- **Same mechanism for Interrupt**: agent-loop.md §5.8/event-log.md §5.8 already require "Sandbox exec kills the process in the container" on `ctx` cancel. This should reuse the identical TERM→grace→KILL path, not a separate immediate-KILL path, so a user-interrupted long build gets the same chance to flush output/clean up as a timeout does.
- Claude Code's own sandbox-runtime confirms the failure mode is real even outside Docker: it currently has **no** SIGTERM-before-SIGKILL step and a killed-by-signal wrapped process reports exit code 0, hiding the kill from the caller ([issues #62987](https://github.com/anthropics/claude-code/issues/62987), [sandbox-runtime#602](https://github.com/anthropics/sandbox-runtime/issues/602)) — a caution to make sure the Sandbox's own exec result is honest about "killed after timeout" rather than reporting a clean exit.
- ⚠ cross-spec: none of agent-loop.md, event-log.md, or research/agent-loop.md fixes the actual grace-period duration — it's explicitly deferred ("Kill mechanics belong to the future sandbox spec"). This doc is that spec's research input; the number itself is Q1 below, not decided here.

## 5. Isolation for multi-tenant untrusted code (must-cover #3)

### 5.1 What primary sources say about Docker alone

Every source that specifically addresses *untrusted, multi-tenant* code execution says plain containers are not enough:
- gVisor's own docs: "containers are not a sandbox" ([gvisor-security-basics-part-1](https://gvisor.dev/blog/2019/11/18/gvisor-security-basics-part-1/)).
- Docker's own security docs concede containers may give "incomplete isolation… in combination with kernel vulnerabilities" ([engine/security](https://docs.docker.com/engine/security/)).
- Concrete recent runc container-breakout CVEs (2025-31133, 2025-52565, 2025-52881) show the shared-kernel risk is not theoretical ([CNCF](https://www.cncf.io/blog/2025/11/28/runc-container-breakout-vulnerabilities-a-technical-overview/)).
- AWS uses Firecracker specifically because "maintaining separate execution environments for individual tenants can limit the impact of executing user-supplied code that might be incorrect or malicious" ([Lambda tenant isolation](https://docs.aws.amazon.com/lambda/latest/dg/tenant-isolation.html)).
- Every hosted "run arbitrary user code" product surveyed in §3.1/3.2 (E2B, Modal, AWS Lambda, GKE Sandbox) uses gVisor or a microVM, never plain runc, for the untrusted-tenant boundary.

⚠ **cross-spec**: ADR 0004 justifies giving the Sandbox a free pass under the Approver because "the container limits the blast radius." ADR 0003 commits only to "Docker now." Taken together as written, that's exactly the configuration every primary source above says is insufficient for code an LLM (possibly acting on attacker-controlled instructions, e.g. prompt injection from a fetched web page) is about to execute. This isn't a contradiction requiring a rewrite — the mitigations below can close the gap without touching either ADR's wording — but it is a real tension worth surfacing before the sandbox spec is written.

### 5.2 Hardening available under "Docker now" without changing the interface

| Control | What it does | Source |
|---|---|---|
| seccomp default profile | blocks ~44 of 300+ syscalls (module loading, mount, etc.) by default | [docs.docker.com/engine/security/seccomp](https://docs.docker.com/engine/security/seccomp/) |
| AppArmor | mandatory access control profile per container (not available in rootless mode) | [docs.docker.com/engine/security/apparmor](https://docs.docker.com/engine/security/apparmor/) |
| `--cap-drop`, drop most capabilities by default | shrinks the kernel-facing privilege surface | [docker run reference](https://docs.docker.com/reference/cli/docker/container/run/) |
| `--security-opt=no-new-privileges` | blocks setuid/setgid privilege escalation inside the container | same |
| user namespaces (`--userns-remap`) / rootless mode | maps container root to an unprivileged host uid; rootless also removes the root daemon | [userns-remap](https://docs.docker.com/engine/security/userns-remap/), [rootless](https://docs.docker.com/engine/security/rootless/) |
| `--read-only` root filesystem | only explicitly granted paths (e.g. the Workspace Volume) are writable | docker run reference |
| `--pids-limit`, `--cpus`, `--memory` | resource ceilings (§9) | docker run reference |
| `--runtime=runsc` (gVisor) | replaces the syscall-passthrough kernel boundary with gVisor's intercepted Sentry (§3.3) | [gvisor architecture](https://gvisor.dev/docs/architecture_guide/intro/) |

All of the first six are compatible with plain Docker and cheap to turn on regardless of which option below is chosen; they don't require redesigning the `Sandbox` interface.

### 5.3 Options

| | A. Docker + runc, hardened flags only | B. Docker + gVisor runtime (recommended) | C. Kata Containers | D. Firecracker directly (E2B-style) |
|---|---|---|---|---|
| Isolation boundary | shared host kernel, narrowed by seccomp/AppArmor/caps/userns | user-space kernel intercepts syscalls | hardware VM (KVM) per container | hardware VM (KVM) per sandbox, jailer-dropped privilege |
| API surface change | none | none (`--runtime=runsc` on `docker run`/daemon config) | needs KVM-capable hosts; still OCI-compatible via `kata-runtime` | different from `docker exec`; would replace the Sandbox's Docker backend entirely |
| Fits "Docker now" (ADR 0003) | yes | yes | yes, with more ops overhead (KVM, extra kernel per sandbox) | no — a separate implementation of the same `Sandbox` interface |
| Addresses §5.1's primary-source concern | partially (still shared kernel) | yes (per gVisor's own stated purpose) | yes | yes |
| Operational cost for a friends-scale project | lowest | low (same container tooling, extra runtime package) | medium (needs `/dev/kvm`, more memory per sandbox) | highest (jailer, image format, network plumbing) |
| Where it fits the roadmap | now | now | later (K8s backend candidate, alongside gVisor) | later, only if the K8s backend needs stronger isolation than gVisor offers |

**Recommend B**: turn on gVisor's `runsc` as the Docker runtime for Sandboxes, on top of the §5.2 hardening flags. It is the one option that closes the primary-source gap without abandoning "Docker now" or changing the `Sandbox` interface's shape — a config change on the Worker's Docker client, not new code. Revisit Kata/Firecracker only if/when the Kubernetes sandbox backend (roadmap) is built, where `agent-sandbox`'s pattern of delegating to a `RuntimeClass` (§3.3) is directly reusable.

## 6. Project files inside the Sandbox container? (must-cover #2)

- TODO.md flags this as unresolved, carried over from provider-gateway grilling. [provider-gateway.md](../design/provider-gateway.md) Decision 23 only puts an index (name, id, size) of project files in the *prompt*, read via the `read_upload` tool — that gets file content into the model's context, not onto disk where a shell command (`pytest`, `grep`, a build) could see it.
- Project files live in S3-compatible object storage (product.md: "Uploads and an Artifacts panel, backed by S3-compatible storage"), not on the Worker's host filesystem, so a Docker **bind mount** from a host path isn't directly available — the Worker would have to stage files somewhere first, which is really a copy, not a mount.

**Options:**

| | (a) Copy-in at Sandbox creation, read-only `/project/…` | (b) No filesystem presence — `read_upload` only | (c) Lazy copy-in on first shell tool use |
|---|---|---|---|
| How | Worker streams each project file from object storage into the container (tar-based copy, the same primitive Docker's `docker cp`/`CopyToContainer` API uses) at Sandbox creation, mounted/placed read-only under `/project` | nothing changes; agent must `read_upload` and then itself write the content to a Workspace Volume path if it wants to run tools against it | same copy-in as (a), but deferred until the first `shell`/file tool call in the session, not paid for sessions that never touch a shell |
| Handles project-file changes mid-session | needs a re-copy step (same "accepted cache break" cost provider-gateway.md already accepts for the prompt index) | not applicable | same re-copy step, only if a Sandbox already exists |
| Cost for the common case (no Sandbox attached) | zero — only paid when a Sandbox exists | zero | zero |
| Matches what other products do | closest to OpenHands' workspace mount and Codex CLI's `--add-dir` writable-root pattern (§3.2) | closest to nothing surveyed — no product makes the agent manually stage files it can already see | variant of (a) |
| Read-only enforceable | yes (`--read-only` + a writable Workspace Volume overlay elsewhere) | n/a | yes |

**Recommendation**: (c) — copy project files into a read-only `/project/…` path only when a Sandbox is actually created for the session (which is already lazy per ADR 0003), refreshed on the same trigger that already invalidates the prompt's project-files index (Decision 23's "accepted cache break"). This keeps zero cost for the common no-Sandbox case, gives shell tools real files to operate on, and reuses the copy-in primitive needed anyway for Uploads (§7) rather than inventing a second one.

## 7. The `Sandbox` interface

product.md fixes the method set's *names* (create, exec, stream, files, stop, resume) but not signatures. Proposed shape, consistent with `CallInput.Sandbox sandbox.Handle` (agent-loop.md) and existing streaming/blob conventions (event-log.md, context.md):

```go
package sandbox

type Handle interface {
    Exec(ctx context.Context, cmd []string, opts ExecOpts) (*ExecResult, error)
    ReadFile(ctx context.Context, path string) ([]byte, error)
    WriteFile(ctx context.Context, path string, data []byte) error
    ListFiles(ctx context.Context, path string) ([]FileInfo, error)
    CopyIn(ctx context.Context, dest string, files map[string][]byte) error  // project files (§6), Uploads
    CopyOut(ctx context.Context, path string) ([]byte, error)                // save_artifact (provider-gateway.md)
}

type ExecOpts struct {
    Timeout  time.Duration      // from ToolDef.Timeout / the Sandbox wall-clock cap (agent-loop.md Decision 11)
    OnOutput func(stream Stream, chunk []byte) // ephemeral, for the live step-card UI — never persisted (§9)
}

type ExecResult struct {
    Stdout, Stderr []byte  // full capture; large results follow the existing >32KB blob_ref + preview rule (event-log.md §3)
    ExitCode       int
    TimedOut       bool
    Killed         bool    // true if the process group was TERM/KILL'd by us, not a clean exit
}
```

- **Streaming**: `OnOutput` feeds the same kind of ephemeral, coalesced channel as `DeltaBus` (event-log.md §5.11: `pg_notify`, coalesced ~50ms, <8KB per message) — live output for the UI's step card, never durable. The durable record is the final `tool.call.completed{result}`, which already follows the generic >32KB-to-blob-storage rule with a 2KB preview (event-log.md §3); no new truncation rule is needed there. A separate hard cap on total captured bytes per call (independent of the blob threshold) protects context size the same way context.md's hard-ceiling truncation already handles one oversized turn (context.md §5.3.3) — this doc doesn't need to re-specify that mechanism, only note that exec output is subject to it like any other tool result.
- **`Exec` always runs the command under `setsid`** and records the PGID so the timeout/Interrupt path (§4) can `kill -TERM -pgid` → grace → `kill -KILL -pgid`.
- **Files**: `ReadFile`/`WriteFile`/`ListFiles` are for the agent's own file tool (editing files it created); `CopyIn`/`CopyOut` are the bulk-transfer primitives used by the platform itself (project files §6, Uploads, and `save_artifact(path)` reading a container path back out per provider-gateway.md).
- **`stop`/`resume`**: not shown above since they operate on the Sandbox as a whole rather than through `Handle` — see §8 for the lifecycle question of what "stop" physically does to the container vs. the Workspace Volume.

## 8. Lifecycle (must-cover #5)

- **Lazy create**: per ADR 0003, attached only when needed (project default, agent request behind approval, or `/remote`). Most sessions never get one.
- **Idle stop**: event-log.md's waiting-states table already says every `awaiting_*`/`sleeping` status "holds no Worker and no Sandbox." So a Sandbox stops the moment a session parks, not just after a separate idle timer — the "idle" that matters is session-level parking, not a standalone container idle-watchdog. **Open**: does "stop" mean `docker stop` (keeps the container, `docker start` again on resume — cheap, but never picks up a rebuilt base image) or does it mean remove the container and keep only the Workspace Volume (resume = fresh container each time, attached to the same volume — costs a re-copy of project files per §6, but naturally picks up image updates)? Neither ADR 0003 nor product.md says which. Given the roadmap item "custom images per project," recreate-on-resume seems more maintainable — flagged as Q6 below.
- **Workspace Volume persistence**: survives while the Sandbox is stopped, deleted after 7 days idle (CONTEXT.md, ADR 0003, product.md all agree — no conflict). This is a Docker named volume backing `/workspace` regardless of which stop/resume model is chosen.
- **⚠ cross-spec — Worker crash / Lease handoff / reattach by id**: event-log.md's `sessions` table (§3) has no `sandbox_id` or container-reference column, and the event catalog's `sandbox.started{sandbox_id, image, reason}` records an id in the log but that's an audit trail, not something a recovering Worker can efficiently query without replaying the whole session. Since a Docker container is a process independent of any Go Worker, it should already outlive a Worker crash physically — the open question is how the *next* Worker (a different process, possibly on a different host) finds it. Two ways: (i) add a `sandbox_id` column to a projection (mirrors how `sessions.status` projects `session.status_changed`); (ii) use **deterministic naming** — e.g. a Docker label `jelly-fish.session_id=<uuid>`, looked up via the Docker API's container-list-by-label filter, needing no schema change at all. **Recommend (ii)**: it needs no new column, and it is naturally idempotent (create-if-absent by label, rather than trusting a possibly-stale stored id). This also answers "does the Sandbox outlive a Worker": yes, physically, as long as recovery can *find* it — which (ii) solves.
- **Long approval waits holding no container**: already decided (ADR 0003 consequence, event-log.md waiting-states table: `awaiting_approval` "holds no Worker and no Sandbox (Sandbox stopped when idle)"). Consistent with the "idle stop = session parks" reading above — nothing new to resolve here, just confirming no conflict.

## 9. Running stdio MCP Connectors inside the Sandbox (must-cover #6)

- ADR 0003 consequence: "Running a user's own stdio MCP server is only possible in a sandboxed session." product.md: "Local (stdio) connectors run only inside the sandbox."
- No jelly-fish doc specifies process lifecycle for these. Two design pressures pull in different directions: (a) a connector process should stay running across multiple tool calls within a session (spinning up a fresh process per call is wasteful and loses any server-side state); (b) the connector's stdin/stdout pipe is naturally attached through *some* process's Docker exec connection, and if that's the Worker's, the pipe dies whenever the Worker's Lease moves (crash, restart, rolling deploy) — exactly the kind of event this event log is built to survive for everything else.
- OpenHands' runtime is the closest working precedent among products surveyed: its own action-execution server runs *inside* the container and exposes a stable HTTP API back to the host process, rather than the host holding a raw stdio pipe into the container (§3.2). That decouples "is the connector process alive" from "is any particular external process still attached to it."
- **Options** (not decided, flagged for the sandbox spec): (i) the Worker starts the stdio connector via `Sandbox.Exec` and holds the pipe itself — simplest, but the connector dies on every Worker crash/Lease handoff and must be restarted by whichever Worker claims the session next; (ii) a small long-lived in-container supervisor (the same PID-1 init already needed for zombie reaping, §4) also multiplexes stdio connector processes and exposes them over a stable channel any Worker can reattach to, surviving Worker crashes without restarting the connector itself. (ii) is more robust but is new code, not just configuration — worth weighing against how often stdio connectors are actually expected to hold important in-memory state (**Unverified** — no jelly-fish doc says).
- **Restarts**: no product surveyed documents an explicit restart/backoff policy for a crashed stdio MCP server; this is genuinely unspecified everywhere, not just here (**Unverified** across primary sources).

## 10. Networking / egress (must-cover #7)

- Base version default: **open egress** (product.md, ADR 0003 says nothing to the contrary — no conflict). Roadmap: "an egress allowlist for sandboxes" later.
- Docker's default bridge network gives containers outbound internet via NAT/masquerading; DNS resolution by container name is only available on user-defined bridge networks, not the default one ([bridge driver docs](https://docs.docker.com/engine/network/drivers/bridge/)). Egress can be fully cut with `--internal` networks, or inter-container traffic blocked with `enable_icc=false` ([network docs](https://docs.docker.com/engine/network/)) — these are the building blocks the later allowlist would use.
- **Cloud metadata endpoint (`169.254.169.254`)**: every major cloud explicitly documents this as a credential-theft vector and recommends blocking it from untrusted workloads — AWS via iptables rules or enforcing IMDSv2 ([EC2 IMDS access limiting](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-metadata-limiting-access.html)), GCP via network policy (with the caveat that blocking it entirely breaks Workload Identity, so GKE Dataplane V2 clusters must explicitly allow it on port 80, [GCP metadata overview](https://docs.cloud.google.com/compute/docs/metadata/overview)), Azure similarly via iptables/NSG rules or an AKS-specific IMDS-restriction feature ([Azure IMDS](https://learn.microsoft.com/en-us/azure/virtual-machines/instance-metadata-service), [AKS imds-restriction](https://learn.microsoft.com/en-us/azure/aks/imds-restriction)).
- ⚠ cross-spec (a gap, not a contradiction): product.md/ADR 0003 describe the base version's egress policy only in terms of the *feature roadmap* ("open network egress" now, "an allowlist" later), with no mention of the metadata endpoint at all. But blocking `169.254.169.254` is a security floor, not a policy feature — if jelly-fish's Worker/Docker host ever runs on a cloud VM (AWS/GCP/Azure), an "open egress" Sandbox can reach the host's own instance metadata and potentially steal the host's cloud credentials, regardless of whether a full domain/IP allowlist exists yet. This should probably be decided independently of, and earlier than, the general allowlist roadmap item (Q7 below).
- Blocking it is cheap under plain Docker networking (an iptables/nftables DROP rule for the container's egress to that one IP), so it doesn't require the gVisor/allowlist decision to land first.

## 11. Metering (must-cover #8)

- product.md already fixes the unit set: "Compute is sampled from Docker stats and stored as usage events in the event log," dashboard shows "sandbox compute (CPU-s, GB-s, disk, egress)," Quotas cover "concurrent sandboxes, compute hours, storage."
- Docker's Engine API stats endpoint `GET /containers/{id}/stats` (and `docker stats`) reports CPU usage, memory usage, network I/O, and block I/O per container ([docker stats CLI](https://docs.docker.com/reference/cli/docker/container/stats/), [runmetrics](https://docs.docker.com/engine/containers/runmetrics/)). Docker's own docs note that recomputing metrics by spawning a new process each time is "relatively expensive," implying the stats endpoint (which streams, rather than re-execing) is the intended integration point rather than periodic ad hoc `docker exec top`-style polling.
- **No primary source (Docker's own docs) states a recommended sampling interval** for the stats stream — this is left to the caller. Given `usage.recorded` already batches per LLM call (event-log.md §3), a natural anchor is to sample Docker stats on some fixed wall-clock tick (e.g. every 10–60s) while a Sandbox is running, converting the delta since the last sample into `usage.recorded{kind: sandbox_cpu | sandbox_mem | ..., quantity, unit}` events, the same "usage" `kind` enum event-log.md's schema already anticipates (`kind text — llm | jev | search | sandbox_cpu | …`). Disk usage (Workspace Volume size) and egress bytes need their own sampling source, since Docker's container stats endpoint covers CPU/memory/block-IO/network-IO but the *volume's* size isn't part of a running container's stats — it would need a periodic `du`-equivalent or Docker's volume inspection, not found documented anywhere as a built-in metric (**Unverified**, likely needs a small in-container or Worker-side check).
- Egress metering specifically: Docker's container stats give total network I/O (in+out across all interfaces), not billed-vs-free split; if an egress allowlist arrives later, "egress" as billed usage would need to be counted as all outbound bytes regardless of allow/deny (simpler, matches "the platform carries real spend" reasoning in ADR 0006) rather than only counting denied/anomalous traffic.

## 12. Base image (must-cover #9)

- Already decided at the product level: "One default image (Python, Node, Go, git, common CLIs)" (product.md). This doc doesn't redesign that; it notes prior-art tradeoffs for whoever builds it.
- Every hosted product surveyed ships one broad default image and lets image size trade off against cold-start time: E2B's is Firecracker-optimized and boots in ~125ms ([firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md) — general Firecracker boot time, not E2B-specific image size); Daytona advertises ~90ms code-to-execution; none of the primary sources give an exact base-image size figure for a Python+Node+Go+git image comparable to what product.md describes (**Unverified** — no source sized such a combined image).
- Pull/caching: Docker's own layer-caching model means the first Sandbox creation on a given Worker host pulls the full image, and every subsequent one on that host is fast; this is standard Docker behavior, not something specific to any surveyed product, and doesn't need new design — just operational awareness that the *first* Sandbox after a Worker/host restart pays the pull cost.
- Custom images (roadmap, later): every hosted product with this feature (E2B templates, Modal `snapshot_filesystem()`) builds a project-specific image once and reuses it, rather than customizing at every Sandbox creation — worth keeping in mind as the shape to copy when that roadmap item is designed, but out of scope for the base version.

## 13. Control channel security and secrets (must-cover #10)

- **Docker socket exposure**: Docker's own docs and the OWASP Docker Security Cheat Sheet are blunt about this — access to `/var/run/docker.sock` "is equivalent to giving unrestricted root access to your host" ([protect-access](https://docs.docker.com/engine/security/protect-access/), [OWASP cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html)). Mounting the socket into any container (even read-only — "only makes it harder to exploit," not safe) grants effective root. Exposing the daemon over unencrypted TCP is equally dangerous. Mitigations Docker documents: SSH-based remote access, or mutual TLS on port 2376 treating the client key like a root password, or (best for jelly-fish's model) never exposing the daemon to any Sandbox container at all — only the Worker process (outside any Sandbox, per ADR 0003's "nothing executes on the host") talks to the Docker daemon, over its local Unix socket or a private network, never reachable from inside a Sandbox.
- This matches ADR 0003's boundary already: the Docker daemon is host-side infrastructure the Worker calls out to, not something a Sandbox (or anything running inside one) should ever reach. Worth stating explicitly in the eventual sandbox spec as an invariant ("the Sandbox network can never route to the Docker control socket/API port"), since it's the kind of thing that's easy to violate by accident (e.g. an overly permissive bridge network shared between the Worker's own containers and Sandboxes, if the Worker itself ever runs containerized).
- **Secrets never entering the Sandbox unless intended**: product.md already establishes Provider Keys are envelope-encrypted and decrypted only in the Worker, never sent to the frontend — and by extension never need to enter a Sandbox, since LLM calls happen from the Worker, not from inside the container. Tool args are scrubbed for known secret header names before being logged (event-log.md payload rules). What's **not** covered by any existing doc: whether a Connector's own credentials (e.g., a local stdio MCP server that itself needs an API key) ever need to be injected into the Sandbox's process environment, and if so, how that's kept out of the Workspace Volume / any files the agent's shell tool could read back and exfiltrate. OpenHands injects such things as `OPENHANDS_SECRET_*` environment variables into its container (§3.2) — a real precedent for "yes, sometimes a secret must enter the Sandbox process, scoped as narrowly as possible," but jelly-fish has no documented answer either way (Q10 below).

## 14. Hard delete (must-cover #11)

- Already decided (event-log.md §5.13): the async cleanup job "deletes blobs by prefix… the Sandbox and Workspace Volume, and Artifacts" after the hard-delete transaction commits. Not redesigned here.
- Given §8's recommendation to identify a session's container by a deterministic label rather than a stored id, hard delete's cleanup job can use the same lookup (`docker ps -a --filter label=jelly-fish.session_id=<id>` equivalent via the Docker API) to find and remove both the container (if still present, per whichever stop model §8 settles on) and the named volume, without needing a stored `sandbox_id` anywhere either — consistent with the rest of this doc's recommendation not to add a new column.
- Deleting a Docker volume (`docker volume rm`) and a container (`docker rm`) are both standard, idempotent Docker Engine API calls; nothing product-specific needed here beyond making sure the cleanup job's retry-on-failure behavior (already specified generically in event-log.md §5.13 for blobs) applies the same way to these two calls.

## 15. Open questions for grilling

- **Q1. Process-group kill grace period?** No primary source fixes one for an agent sandbox specifically; Docker's own `docker stop` default is 10s ([docker docs](https://docs.docker.com/reference/cli/docker/container/stop/)). Proposed: 5s TERM→KILL grace for exec'd commands (shorter than container-teardown, since this interrupts a command the user is actively waiting on), same grace period reused for Interrupt as for timeout. Tune with evals.
- **Q2. Does "stop" keep the container (docker stop/start) or remove it and recreate on resume?** Neither ADR 0003 nor product.md says. Proposed: remove-and-recreate-from-Workspace-Volume on resume, so image updates and project-file copy-ins (§6) apply naturally; the tradeoff is paying the copy-in cost again on every resume.
- **Q3. How does a Worker find/reattach to a session's running container after a crash, with no `sandbox_id` column in `sessions`?** Proposed: a deterministic Docker label (`jelly-fish.session_id=<uuid>`), looked up via the Docker API's list-by-label filter — no schema change, naturally idempotent create-if-absent. Needs a nod in event-log.md's data model or this spec's own.
- **Q4. Do project files get copied into the Sandbox filesystem?** Proposed: yes, lazily, only when a Sandbox is created for a session with project files, read-only under `/project/…`, re-copied on the same "accepted cache break" trigger provider-gateway.md Decision 23 already accepts for the prompt index.
- **Q5. Plain Docker/runc, or Docker+gVisor, for the base version?** Every primary source on multi-tenant untrusted code (gVisor's own docs, AWS's Firecracker rationale, recent runc CVEs) says plain containers aren't a security boundary. Proposed: Docker + `runsc` (gVisor) runtime, kept alongside the seccomp/AppArmor/userns/cap-drop/read-only-root hardening flags — a config change, not a new `Sandbox` implementation. Revisit Kata/Firecracker only for the Kubernetes-backend roadmap item.
- **Q6. Should the base version block the cloud metadata endpoint (`169.254.169.254`) even though the general egress allowlist is a "later" roadmap item?** Proposed: yes, as a day-one security floor independent of the allowlist feature — a single iptables/nftables DROP rule for that one IP, cheap under plain Docker networking, closing an SSRF-to-cloud-credential-theft path that every major cloud provider documents as real.
- **Q7. Sampling interval and disk/egress source for sandbox compute metering?** Docker's stats endpoint gives CPU/memory/network-IO/block-IO but not Workspace Volume disk usage. Proposed: sample Docker stats on a fixed tick (10–60s) while a Sandbox is `running`, emit deltas as `usage.recorded{kind: sandbox_cpu|sandbox_mem|sandbox_disk|sandbox_egress}`; disk needs a separate periodic volume-size check since it's not part of container stats. Tune the interval with evals; no primary source recommends one.
- **Q8. How are stdio MCP Connector processes supervised across a Worker crash/Lease handoff?** No product surveyed documents a restart/backoff policy for this exact case. Proposed: either the simplest option (Worker holds the pipe, restarts the connector itself on the next claim) or a small in-container supervisor that survives independently of any one Worker (more robust, more new code) — genuinely open, needs a decision in the sandbox spec.
- **Q9. Exec output streaming vs. durable result — same size rules as everywhere else, or does exec need its own cap?** Proposed: live streaming reuses the `DeltaBus` ephemeral/coalesced convention (event-log.md §5.11); the durable `tool.call.completed` result reuses the existing >32KB blob_ref + preview rule (event-log.md §3) and context.md's hard-ceiling truncation for prompt inclusion — no new mechanism needed, just confirm exec results aren't special-cased.
- **Q10. Do Connector secrets ever need to enter the Sandbox's process environment, and how are they kept from leaking into the Workspace Volume or an Artifact?** No jelly-fish doc addresses this. OpenHands' `OPENHANDS_SECRET_*` env-var convention is a working precedent (§13) but not necessarily the right one here, since jelly-fish's Provider Keys explicitly never leave the Worker (product.md) — whether the same rule should extend to *Connector* credentials is undecided.
