## 1. Summary

- **Login options**: passkeys (WebAuthn) are the strongest option for non-technical friends — phishing-resistant, no password to remember, and platform support is now broad (§2.2). Magic link and email OTP are simpler to build and are reasonable fallbacks, each with known pitfalls (link-prefetch invalidation; OTP brute force) that have documented mitigations. Google/GitHub OAuth is easy for technical friends, adds zero password surface, but ties login to a third party's uptime and requires a consent-screen setup regardless of how few users there are. Argon2id-hashed passwords per OWASP are a safe fallback but the weakest UX for non-technical users. **Build vs hosted** is a real fork: Ory Kratos and Zitadel are free, self-hostable, and support passkeys + magic link + OIDC out of the box; Clerk/WorkOS/Supabase Auth are hosted (Supabase is also self-hostable) with generous free tiers but gate some features (Clerk: passkeys need a paid plan) — see §2.6.
- **Login Session for the web app**: OWASP recommends server-side sessions (opaque ID in an `HttpOnly`, `Secure`, `SameSite` cookie, ideally `__Host-`-prefixed) over JWTs for exactly the property jelly-fish needs — "log out everywhere" is an instant DB delete, whereas a JWT stays valid until it expires no matter what the server does (§3.1). CSRF needs a token-based defense in addition to `SameSite`, per OWASP's own conditions for when `SameSite` alone would be enough (§3.2). **⚠ cross-spec**: [event-log.md §5.12](../design/event-log.md) specs the SSE endpoint (`GET /sessions/{id}/events`) but never says how it authenticates — the browser `EventSource` API cannot send a custom `Authorization` header at all, which makes cookie-based Login Session auth close to mandatory for that endpoint specifically (§3.3).
- **CLI auth**: RFC 8628 Device Authorization Grant is the standard pattern for a CLI with no local browser-embeddable redirect, used by GitHub CLI and (as of 2026) Vercel CLI; Fly's `flyctl` instead does browser-based login or email/password/OTP flags. All of them keep long-lived tokens in the OS keychain via a Go library (`99designs/keyring` or the `zalando/go-keyring` fork) rather than a plaintext file (§4).
- **Invite-only signup and admin bootstrap**: common self-hosted pattern — first registered user becomes admin (race-safe, inside a transaction, only while the users table is empty), then registration closes to invite-only; Ghost CMS's team-invite flow is one clean documented precedent (§5). Nothing in jelly-fish's ground truth designs this yet, and CONTEXT.md's Quota already assumes an admin role exists.
- **Provider Key storage**: envelope encryption (a DEK encrypts the key, a KEK — currently `JF_MASTER_KEY` — wraps the DEK) is the standard AWS/Google pattern; AES-256-GCM with a 96-bit nonce and no nonce reuse is the standard AEAD choice, with AAD binding the ciphertext to `(user_id, provider)` so a row can't be swapped between users; Go's `crypto/cipher` AEAD interface supports this directly (§6). Go itself has no reliable way to zero secrets from memory (open issue on the Go tracker); `memguard` is a third-party mitigation, not a guarantee (§6.6).
- **Provider-specific**: Anthropic and OpenAI both support scoped keys with spend limits (Anthropic Workspaces, OpenAI Projects); Gemini keys support IP/referrer/API restrictions but quota is per-project, not per-key (§7.1–7.3). **Important, verified carefully**: neither Anthropic nor OpenAI offers an OAuth flow a third-party app like jelly-fish could use to get a metered API key on a user's behalf — only OpenRouter (not one of jelly-fish's three Providers) documents this pattern (§7.4). This confirms BYOK-by-pasting-a-key is the only real option for the base version; "Sign in with Provider" for API access isn't available from Anthropic or OpenAI as of this research.
- **Platform secrets**: Jev/TypeSafe's key, search Provider keys, VAPID keys (RFC 8292), SMTP credentials, and the Telegram bot token are all platform-operator secrets, not per-user Provider Keys — they don't need per-row envelope encryption or a `key_id`, just the same "env var / secret file, never logged" treatment (§8).
- **Security references**: OWASP ASVS 5.0 renumbered its Authentication and Session Management chapters to V6/V7; the Authentication Cheat Sheet's guidance on lockout (tied to the account, not the IP) and rate limiting maps directly onto jelly-fish's small-friends-scale login; the Logging Cheat Sheet is explicit that secrets/keys/passwords must never be logged, which is already jelly-fish's Event Log rule (§9).

## 2. Login options for Users

### 2.1 Email magic link vs email OTP

Both are "passwordless" in the sense of not needing a memorized secret, but have different failure modes.

- **Magic link pitfall — link prefetching**: corporate email security gateways (e.g. Outlook Safe Links, Mimecast) open every link in an email automatically before the human ever sees it, which consumes a naive single-use token immediately; the user's own click then fails. Mitigation: make the emailed link's `GET` a no-op redirect to a confirmation page, and only consume the token on the user's own `POST`/click-through action ([mojoauth.com — Are Magic Links Secure?](https://mojoauth.com/blog/are-magic-links-secure-technical-deep-dive)) **Unverified**: this is a secondary source, not a spec, but the mechanism (prefetch bots vs `GET`-is-safe) is standard web practice.
- **OWASP Forgot Password Cheat Sheet** on token-based recovery/login links: tokens should be cryptographically random, sufficiently long, single-use, short-lived (the cheat sheet's own guidance trends toward well under an hour), transmitted only over HTTPS, and rate-limited ([cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)).
- **OTP pitfall — brute force**: a 6-digit code has only 1,000,000 possibilities; without rate limiting it's guessable well within a short link's validity window. NIST SP 800-63B requires throttling of failed authentication attempts ([pages.nist.gov/800-63-3/sp800-63b.html](https://pages.nist.gov/800-63-3/sp800-63b.html)).
- **OWASP Authentication Cheat Sheet** covers rate limiting/lockout generally (not magic-link/OTP specifically): lock counts should be tied to the account, not just the source IP, since an attacker can distribute guesses across many IPs ([cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)).

### 2.2 Passkeys (WebAuthn)

- **W3C WebAuthn Level 3** ([w3.org/TR/webauthn-3](https://www.w3.org/TR/webauthn-3/)) defines the passkey as a client-side discoverable credential: registration creates an asymmetric key pair, the private key never leaves the device/platform authenticator, and the public key is what the Relying Party stores. Multi-device ("synced") passkeys replicate the private key across a user's devices via the platform's own sync (iCloud Keychain, Google Password Manager) — the Relying Party never sees this replication.
- **FIDO Alliance** describes passkeys as phishing-resistant by construction, because the credential is cryptographically bound to the origin that registered it — a look-alike phishing domain simply can't get the browser to release a signature ([fidoalliance.org/passkeys](https://fidoalliance.org/passkeys/)).
- **Go library**: `github.com/go-webauthn/webauthn` is a FIDO2-conformant WebAuthn server-side library; its README states current Go version support (1.25–1.27) and lists supported attestation formats and extensions (PRF, Large Blob, Credential Protection). The app implements `webauthn.User` and stores `webauthn.Credential` structs — this is the integration surface jelly-fish would use ([github.com/go-webauthn/webauthn](https://github.com/go-webauthn/webauthn)).
- **PWA support (2026)**: WebAuthn is available in Safari on iOS and Chrome on Android, including inside an installed PWA, not just the browser tab ([progressier.com/pwa-capabilities/biometric-authentication-with-passkeys](https://progressier.com/pwa-capabilities/biometric-authentication-with-passkeys)). A third-party tracking site reports iOS Safari passkey availability near 100% of iOS users as of March 2026, with iCloud Keychain sync ([state-of-passkeys.io/ios](https://state-of-passkeys.io/ios)) — **Unverified**: that figure is a third-party tracker, not an Apple primary source, and no primary Apple/Google source was found confirming feature parity between installed-PWA WebAuthn and in-browser WebAuthn (e.g. conditional UI/autofill). Treat "passkeys work in our installed PWA" as needing its own manual verification pass on real iOS/Android devices before relying on it.

### 2.3 OAuth / OIDC sign-in (Google, GitHub)

- **Google OpenID Connect** requires registering an OAuth client (Client ID/secret) and a consent screen in Google Cloud Console regardless of app size; consent screen size scales with requested scopes, and Google's own advice is to request as few scopes as possible to keep the consent screen short ([developers.google.com/identity/openid-connect/openid-connect](https://developers.google.com/identity/openid-connect/openid-connect)).
- **GitHub OAuth Apps**: registration and permission/authorization setup is documented at [docs.github.com/en/apps/oauth-apps](https://docs.github.com/en/apps/oauth-apps); no separate small-scale exemption was found.
- Neither requires "verification" review at friends-scale the way a public consumer app would (Google's verification review is triggered by requesting sensitive/restricted scopes or exceeding a user count, not by existing at all) — but this doc did not find a primary source giving an exact user-count threshold, so treat any specific number as **Unverified**.

### 2.4 Passwords (if offered as a fallback)

- **NIST SP 800-63B-4** (verified 2026-09-27, [pages.nist.gov/800-63-4/sp800-63b.html](https://pages.nist.gov/800-63-4/sp800-63b.html)): passwords used as the only factor must be at least **15** characters (8 only when part of MFA); the older 800-63-3 minimum of 8 is superseded. Still explicitly *do not* impose composition rules (mixed case/digit/symbol requirements) or periodic forced rotation; verifiers *must* check new passwords against a corpus of known-breached/common passwords and reject matches ([pages.nist.gov/800-63-3/sp800-63b.html](https://pages.nist.gov/800-63-3/sp800-63b.html)).
- **OWASP Password Storage Cheat Sheet**: Argon2id minimum configuration `m=19456` (19 MiB), `t=2`, `p=1`, with documented equal-security alternatives at other memory/time trade-offs ([cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)).

### 2.5 Account recovery trade-offs

- **Passkey loss** (lost/wiped device, no other device with a synced copy): the platform's own sync (iCloud Keychain, Google Password Manager) is the primary recovery path; if that's also gone, the app needs a fallback authenticator (a second passkey registered in advance, or falling back to email). Verified against NIST SP 800-63B-4 ([pages.nist.gov/800-63-4/sp800-63b.html](https://pages.nist.gov/800-63-4/sp800-63b.html)): syncable authenticators (synced passkeys) are allowed at AAL2 and barred only at AAL3; "Email SHALL NOT be used for out-of-band authentication" (it's SMS/PSTN that is "restricted"). So by NIST's bar a magic link is a weaker login than a passkey; fine at friends scale, but it's the weak link.
- **Magic-link/password-reset loses value if the user loses their email account** — whoever controls the email controls the login. This is the single shared weak point across magic link, OTP, and password-reset flows; passkey-only accounts don't have it (no email round-trip needed to *log in*, only potentially to *add a new device*).
- **OWASP Forgot Password Cheat Sheet** reiterates the same token-hygiene rules (§2.1) apply to recovery links specifically ([cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)).

## 3. Login Session management for the web app

### 3.1 Server-side session cookie vs JWT

OWASP's Session Management Cheat Sheet is unambiguous: prefer server-side sessions (an opaque, unguessable session ID as a cookie value, mapped to state in the DB) over JWTs for browser apps, and never put a JWT, session ID, or any credential in `localStorage`/`sessionStorage` ([cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). Specifics:
- Cookie flags: `HttpOnly` (blocks JS/XSS access), `Secure` (HTTPS only), `SameSite=Strict` or `Lax`, and the `__Host-` prefix (forces `Secure`, no `Domain` attribute, `Path=/` — blocks subdomain cookie-tossing attacks).
- Rotate/regenerate the session ID on any privilege-level change (login, password change) to prevent session fixation.
- **Why this matters for jelly-fish specifically**: "log out everywhere" and revoking a compromised Login Session is a single DB delete with a server-side session store; a JWT keeps working until it expires no matter what the server does, unless a separate revocation/deny-list is built — which is extra machinery a server-side session store doesn't need. This lines up with the Event Log architecture's own bias toward "the DB row is the truth" (ADR 0001) rather than a self-contained signed token.

### 3.2 CSRF

OWASP's CSRF Prevention Cheat Sheet treats the synchronizer token pattern (per-Login-Session unpredictable token, checked server-side on every state-changing request) as the primary defense, and `SameSite` cookies as defense-in-depth only ([cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). OWASP lists specific conditions under which `SameSite` alone would be enough (no shared registrable domain with untrusted hosts, zero state-changing `GET` endpoints, `SameSite=Strict` + `__Host-`, Origin/Referer verification, and accepting residual risk on old browsers) — meeting all of them is a real design commitment, not a default.

Verified 2026-09-27: the cheat sheet now also lists **Fetch Metadata** (`Sec-Fetch-Site`) as an alternative for apps that target only modern browsers, with an Origin check as the mandatory fallback; the synchronizer token stays the default for stateful apps. **Go 1.25 ships this as `http.CrossOriginProtection`** ([pkg.go.dev/net/http#CrossOriginProtection](https://pkg.go.dev/net/http#CrossOriginProtection)): wrap the mux, and non-safe (POST/PUT/DELETE…) cross-origin browser requests are rejected using `Sec-Fetch-Site`, falling back to comparing `Origin` with `Host`; GET/HEAD/OPTIONS always pass. jelly-fish's PWA targets modern browsers only, and state changes are never GET, so this is a real option next to (or instead of) tokens.

### 3.3 SSE / EventSource cookie-auth implication — ⚠ cross-spec

The browser `EventSource` API has no way to attach a custom `Authorization` header ([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)); its only cross-origin credential option is `withCredentials: true`, which sends cookies. [event-log.md §5.12](../design/event-log.md) specs `GET /sessions/{id}/events` (the SSE endpoint) with `authz via TenantScope` but never says what carries the identity into that check. If the Login Session is cookie-based (§3.1), this is free — the browser attaches the cookie automatically. If jelly-fish ever leans toward bearer tokens for the rest of the API, the SSE endpoint would need its own carve-out (a short-lived signed query param, generally discouraged since query strings leak into logs/referrers, or a cookie used *only* for this one endpoint). This doc flags it; the design doc should state which one explicitly.

## 4. CLI auth

jelly-fish's CLI is roadmap, but product.md already says it shares the Slash Command registry with the web app, so its auth model needs to fit the same tenancy/session story.

- **RFC 8628 OAuth 2.0 Device Authorization Grant** ([rfc-editor.org/rfc/rfc8628](https://www.rfc-editor.org/rfc/rfc8628)): the device requests a `device_code` + short human-typeable `user_code`; the user opens a verification URL on any other device/browser and enters the code; the CLI polls the token endpoint until the user approves (or denies/expires), with a server-dictated minimum poll interval and a `slow_down` response if it polls too fast. Designed exactly for "no local browser redirect" tools like a CLI.
- **GitHub CLI (`gh`)**: `gh auth login` defaults to the browser-based OAuth Device Flow; the resulting token is stored in the OS's secure credential store, falling back to a plaintext file only if no credential store is found. `gh` also supports a personal-access-token path (`--with-token`) and a `GH_TOKEN` env var for CI ([cli.github.com/manual/gh_auth_login](https://cli.github.com/manual/gh_auth_login)).
- **Vercel CLI**: as of a 2026 changelog, `vercel login` moved to RFC 8628 Device Flow as its primary method, deprecating the older email-link and per-provider (`--github`/`--gitlab`/`--bitbucket`) login flags; `VERCEL_TOKEN` is the recommended env var for CI/CD ([vercel.com/changelog/new-vercel-cli-login-flow](https://vercel.com/changelog/new-vercel-cli-login-flow), [vercel.com/docs/cli/login](https://vercel.com/docs/cli/login)).
- **Fly.io `flyctl`**: defaults to browser-based login (not RFC 8628 device flow specifically), with `--email`/`--password`/`--otp` flags for non-browser use, and `FLY_API_TOKEN`/`FLY_ACCESS_TOKEN` env vars for CI; it also supports minting scoped tokens (`fly tokens create deploy -a <app>`) ([docs.fly.io/flyctl/auth-login](https://docs.fly.io/flyctl/auth-login/)).
- **Claude Code CLI**: official docs say `claude` opens "browser prompts" to authenticate, or accepts `ANTHROPIC_API_KEY` directly with a one-time approval prompt ([code.claude.com/docs/en/setup](https://code.claude.com/docs/en/setup)). The exact OAuth flow type (device flow vs authorization-code-with-local-redirect) is not stated in that page — **Unverified**.
- **Token storage**: `github.com/99designs/keyring` and the separate, simpler `github.com/zalando/go-keyring` (not a fork; verified 2026-09-27) wrap macOS Keychain, Windows Credential Manager, and Linux Secret Service (GNOME Keyring/KWallet) behind one Go interface — the standard way a Go CLI avoids a plaintext token file ([github.com/99designs/keyring](https://github.com/99designs/keyring)).

For jelly-fish: Device Authorization Grant (RFC 8628) matches the GitHub CLI / Vercel CLI precedent and needs no browser embedded in the CLI process; the issued token should be a long-lived opaque token tied to the same Login Session / revocation model as the web app (so "log out everywhere" also kills CLI sessions), stored via an OS-keychain library, never a plaintext `~/.jellyfish/token` file by default.

## 5. Invite-only signup and admin bootstrap

No ground-truth doc designs this yet, even though CONTEXT.md's Quota is explicitly "set by an admin" — an admin role is assumed but never created anywhere.

- **First-user-becomes-admin bootstrap** is a common self-hosted pattern: while the `users` table is empty, the next registration becomes admin; this must run inside a transaction/lock so two simultaneous first registrations can't both become admin, and the path must be unreachable once any user exists. This is a widely repeated implementation pattern across small self-hosted projects (seen in multiple project issue trackers describing exactly this requirement) rather than something with one canonical spec — treat the *shape* of the pattern as solid, and any specific project's code as illustrative, not authoritative.
- **Grafana** ships a simpler variant: `GF_SECURITY_ADMIN_USER` / `GF_SECURITY_ADMIN_PASSWORD` env vars seed the one admin account, but only on the very first startup before any data exists — changing them later has no effect on an already-initialized instance ([grafana.com/docs/grafana/latest/setup-grafana/configure-grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/); behavior corroborated by [Grafana community/GitHub issue discussion](https://github.com/grafana/grafana/issues/55887)).
- **Ghost CMS**'s invite-only model is a clean documented precedent for "after bootstrap, only an existing Owner/Administrator can add more people": Settings → Staff → Invite people sends an email invite; the recipient sets a password to activate; the Owner role can't be deleted ([ghost.org/help/managing-your-team](https://ghost.org/help/managing-your-team/)).

For jelly-fish's friends-scale, one plausible shape (not a decision — flagged as an open question): first registration becomes admin; after that, an allowlist of invited emails (or an admin-generated invite link) gates further sign-ups, since there's no self-serve public signup use case at all here.

## 6. Provider Key storage: envelope encryption

Already decided: `JF_MASTER_KEY` from env/secret file, `key_id` per row, KMS later (ground truth above). This section is the supporting primary-source research for *how* to implement that.

### 6.1 Envelope encryption pattern

Standard shape, described identically by both major clouds: generate a fresh Data Encryption Key (DEK) for the data being protected, encrypt the data locally with the DEK, then encrypt (wrap) the DEK with a centrally-managed Key Encryption Key (KEK); only the KEK needs to live in a vault/KMS, and the wrapped DEK can be stored right next to the ciphertext ([cloud.google.com/kms/docs/envelope-encryption](https://cloud.google.com/kms/docs/envelope-encryption), [docs.aws.amazon.com/kms/latest/developerguide/concepts.html](https://docs.aws.amazon.com/kms/latest/developerguide/concepts.html)). For jelly-fish, `JF_MASTER_KEY` (or its KMS successor) plays the KEK role; whether the DEK is per-row or the master key encrypts Provider Keys directly (no separate per-row DEK) is an open question (§ below) — both are legitimate variants of the same pattern.

### 6.2 AES-256-GCM nonce rules

NIST SP 800-38D specifies a 96-bit (12-byte) nonce as the standard IV length for GCM, and states that reusing a nonce with the same key is catastrophic — it can leak the authentication key and break confidentiality/integrity for every message encrypted under that key with that nonce ([nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)). For a single key encrypting many rows with randomly generated 96-bit nonces, NIST's own collision-probability bound caps safe usage at roughly 2^32 encryptions before the birthday-bound risk becomes non-negligible — well beyond friends-scale traffic, but worth knowing if a single master key is reused across a very large number of rows over the platform's lifetime. A deterministic counter nonce removes this ceiling entirely but requires guaranteeing the counter is never reused (e.g. across restarts) — harder to get right by hand than "generate 12 random bytes per encryption," which is the simpler and standard choice at this scale.

### 6.3 AAD binding to (user_id, provider)

Go's `crypto/cipher` AEAD interface (`Seal(dst, nonce, plaintext, additionalData)` / `Open(dst, nonce, ciphertext, additionalData)`) authenticates but does not encrypt `additionalData` ([pkg.go.dev/crypto/cipher#AEAD](https://pkg.go.dev/crypto/cipher#AEAD)). Passing something like `user_id || provider` as AAD means `Open` fails if a ciphertext is ever read back against the wrong row's context — the standard mitigation for "row swapping"/confused-deputy at the storage layer, and a direct match for the mcp-client.md pattern of keying credentials by `(project_id, connector_id)`.

### 6.4 Google Tink (Go)

`github.com/tink-crypto/tink-go` provides AEAD primitives (AES-GCM, AES-GCM-SIV, ChaCha20-Poly1305, XChaCha20-Poly1305) and first-class envelope-AEAD/keyset support (`KeysetHandle`, primary-key rotation without touching call sites) ([pkg.go.dev/github.com/tink-crypto/tink-go/v2](https://pkg.go.dev/github.com/tink-crypto/tink-go/v2), [developers.google.com/tink](https://developers.google.com/tink)); the repository shows active recent releases ([github.com/tink-crypto/tink-go](https://github.com/tink-crypto/tink-go)). Using Tink instead of hand-rolled `crypto/cipher` trades a small amount of flexibility (Tink's keyset format is opinionated) for built-in key-rotation bookkeeping — relevant since `key_id`-based rotation is already the decided design.

### 6.5 Key rotation via `key_id`

Both AWS KMS (which internally tracks which key-material version encrypted which ciphertext so decryption of old data still works after rotation) and Tink (a keyset holds multiple key versions, one marked primary; new data uses the primary, old data still decrypts against its original key) describe the same general shape jelly-fish already decided: store which key encrypted a row, keep old keys available for decryption, only new writes use the new key ([docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html](https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html), [developers.google.com/tink/managing-key-rotation](https://developers.google.com/tink/managing-key-rotation)).

### 6.6 Memory hygiene in Go

Go's garbage collector can move/copy memory and gives no built-in guarantee of zeroing a byte slice after use; there's an open Go tracker issue (#21865) requesting a `runtime/secret`-style facility for secure key erasure, still not shipped as of this research ([github.com/golang/go/issues/21865](https://github.com/golang/go/issues/21865)). `github.com/awnumar/memguard` is a third-party library offering `mlock`-backed, guard-paged buffers with an explicit `Destroy()` — real mitigation, but a pre-1.0, opt-in dependency, not a language guarantee ([pkg.go.dev/github.com/awnumar/memguard](https://pkg.go.dev/github.com/awnumar/memguard)). For jelly-fish: a decrypted Provider Key lives in the Worker process only for the duration of one Provider call (already the architecture — [provider-gateway.md](../design/provider-gateway.md) §6 "only `ListModels(ctx)` touches a decrypted key, and only from the Worker"); this narrows the exposure window regardless of whether memguard-style hardening is added.

### 6.7 Masking and deletion

Showing only the last 4–6 characters of a key in the UI is standard practice at Stripe (explicitly recommended for logs and UI) and used in GitHub's own token format design ([docs.stripe.com/keys-best-practices](https://docs.stripe.com/keys-best-practices), [github.blog — Behind GitHub's new authentication token formats](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)). Deletion (removing the row and its ciphertext) is a form of NIST SP 800-88's "cryptographic erasure" concept — destroying the key material renders the ciphertext permanently unrecoverable even before physical storage is overwritten ([nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-88r2.pdf](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-88r2.pdf)) — a hard `DELETE` of the row is sufficient; no special crypto-shredding machinery is needed since the DEK/row and the ciphertext are already deleted together.

## 7. Provider-specific: key restrictions, spend limits, and OAuth-to-provider

### 7.1 Anthropic

Anthropic supports Workspaces (a grouping above individual API keys) with per-Workspace custom spend and rate limits, configured through the Admin API; keys can be scoped to a specific Workspace ([docs.anthropic.com/en/api/administration-api](https://docs.anthropic.com/en/api/administration-api), [docs.anthropic.com/en/api/admin-api/workspaces/create-workspace](https://docs.anthropic.com/en/api/admin-api/workspaces/create-workspace)). Advice for jelly-fish users: create a dedicated Workspace with its own spend limit for the key they hand to jelly-fish, rather than using an org-wide key.

### 7.2 OpenAI

OpenAI's Projects let a user generate an API key scoped to just that project, with hard spend limits that return `429`/`project_spend_limit_exceeded` once hit, and per-project, per-model rate limits settable by the org Owner ([help.openai.com — Managing your work with Projects](https://help.openai.com/en/articles/9186755-managing-your-work-in-the-api-platform-with-projects), [developers.openai.com/api/docs/guides/spend-limits](https://developers.openai.com/api/docs/guides/spend-limits)). Same advice: a dedicated Project + key with a spend cap.

### 7.3 Gemini

Gemini/Google AI Studio keys can be restricted to the Generative Language API only, and further restricted by HTTP referrer, IP address, or app identifier through Google Cloud Console's API key restriction settings ([ai.google.dev/gemini-api/docs/api-key](https://ai.google.dev/gemini-api/docs/api-key), [cloud.google.com/docs/authentication/api-keys](https://cloud.google.com/docs/authentication/api-keys)). Rate limits, however, are enforced per *project*, not per key — multiple keys under one project share the same quota ([ai.google.dev/gemini-api/docs/rate-limits](https://ai.google.dev/gemini-api/docs/rate-limits)), so a spend cap per se isn't a first-class Gemini key feature the way it is for Anthropic/OpenAI.

### 7.4 "Sign in with Provider" for API access — verified carefully

- **Anthropic**: docs describe OAuth bearer-token auth for Claude Code's own login, not a documented OAuth flow for third-party apps to obtain a metered API key on a user's behalf ([docs.anthropic.com/en/docs/claude-code/iam](https://docs.anthropic.com/en/docs/claude-code/iam)). **Unverified / not found**: no primary source confirms a third-party-usable OAuth-for-API-billing flow.
- **OpenAI**: an open community feature request exists for exactly this ("let third-party apps use my ChatGPT subscription via OAuth"), which is itself evidence it doesn't exist today ([community.openai.com/t/...1395942](https://community.openai.com/t/feature-request-consumer-delegated-ai-access-let-third-party-apps-use-my-ai-subscription-via-oauth/1395942)). **Not available.**
- **Gemini**: Google does document general OAuth 2.0 client credentials for accessing user *data* via Google APIs ([ai.google.dev/gemini-api/docs/oauth](https://ai.google.dev/gemini-api/docs/oauth)), but no primary source found ties this to a third party obtaining metered *Gemini API* billing on the user's behalf. **Unverified.**
- **OpenRouter** (not one of jelly-fish's three Providers, cited only as the pattern precedent the research prompt asked to verify) does document OAuth PKCE for third-party apps: the app redirects the user to OpenRouter, gets an authorization code, exchanges it for a user-controlled API key the app can then use, with the user able to set a credit limit on that key ([openrouter.ai/docs/guides/overview/auth/oauth](https://openrouter.ai/docs/guides/overview/auth/oauth), [openrouter.ai/docs/use-cases/byok](https://openrouter.ai/docs/use-cases/byok)).

**Conclusion for jelly-fish**: pasting a Provider Key (BYOK, already the decided model per ADR 0006) is the only way to connect Anthropic or OpenAI today. There is no OAuth-based alternative to research further for those two; Gemini's OAuth is unverified for this specific use and not worth pursuing without a clearer primary source.

## 8. Platform secrets (not per-user Provider Keys)

These are operator-held secrets, one per deployment, not one per User — no `key_id`/rotation-per-row scheme is needed, just "env var / secret file, never logged, never in Event Log payloads," the same rule the Event Log already states generally ([event-log.md §6](../design/event-log.md)).

- **Jev/TypeSafe key**: the Approver's Jev calls are metered as a Platform Service ([approver.md §9 Decision 15](../design/approver.md), [CONTEXT.md](../../CONTEXT.md) "Jev", "Platform Service"); whatever credential authenticates jelly-fish to TypeSafe is a single operator secret.
- **Search Provider keys** (Brave/Tavily): also Platform Services by default, with users able to optionally bring their own ([ADR 0006](../adr/0006-byok-llm-platform-metered-services.md), [product.md](../product.md) "Tools and MCP"). The platform's own default key is an operator secret; a user's own is technically closer to a Provider Key (should probably reuse the same envelope-encryption path, not a new one).
- **VAPID keys** (Web Push): RFC 8292 defines VAPID as an EC (P-256) key pair the application server uses to sign a JWT identifying itself to the push service; the private key must stay secret ([rfc-editor.org/rfc/rfc8292](https://www.rfc-editor.org/rfc/rfc8292)).
- **Telegram bot token**: Telegram's own Bot API docs say the token is the bot's unique identifier, must be kept secret like a password, and can be revoked via BotFather at any time ([core.telegram.org/bots/api](https://core.telegram.org/bots/api)). This token effectively is the Telegram Channel's credential.
- **SMTP credentials**: no dedicated spec found; general practice is identical to the others — env var/secret file, rotated by re-issuing at the SMTP provider.

All of these fit the general pattern (env var / secret file today, same interface a KMS could sit behind later) without needing the per-row `key_id` machinery Provider Keys and Connector credentials need, since there's exactly one live value at a time per secret, not one row per User.

## 9. Security references

- **OWASP ASVS**: current stable version is 5.0.0; Authentication and Session Management moved to chapters V6 and V7 respectively (previously V2/V3 in 4.x), explicitly aligned to be "a compliant subset of selected NIST 800-63B controls" ([owasp.org/projects/asvs](https://owasp.org/projects/asvs), [github.com/OWASP/ASVS/tree/v5.0.0/5.0/en](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0/en)).
- **Rate limiting login**: OWASP Authentication Cheat Sheet recommends locking on the account identity (not just source IP, since an attacker can spread guesses across IPs) and applying MFA as the strongest available mitigation ([cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)).
- **Audit log of key changes**: OWASP Logging Cheat Sheet lists authentication events and administrative/privilege changes as things that *should* be logged, and explicitly lists passwords, credentials, session IDs, tokens, and encryption keys as things that *must never* be logged in cleartext ([cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)) — this matches the Event Log's existing rule that secrets never enter payloads; a Provider-Key-changed audit trail would log the *event* (which User, which Provider, added/rotated/deleted, when) never the key material itself.

## Open questions for grilling

0. **Big shape: how do Users log in, and do we build or adopt?** Proposed: passkeys (WebAuthn via `go-webauthn`) as the primary method for friends-scale non-technical Users, with email magic link as the fallback for a device with no passkey yet; Google OAuth optional for the technically inclined; no password option in the base version (removes an entire OWASP-cheat-sheet's worth of storage/rotation/lockout concerns). Hand-rolled on Go + Postgres rather than an external auth provider, matching the project's "own it" ethos (ADR 0001) and its "learning project" goal (product.md). Touches: `users` table design, session/login endpoints, product.md "Tenancy and auth", the whole rest of this doc's §2–§3.

1. **What replaces "Session" for the login concept, and where does it get defined?** Proposed: `Login Session` (this doc's placeholder) or `Web Session`; add it to CONTEXT.md's Tenancy section, explicitly distinguished from `Session` (a conversation). Touches: CONTEXT.md, every future auth/session doc, the SSE endpoint's docs.

2. **Server-side session cookie or JWT for the web app's Login Session?** Proposed: server-side session (opaque ID in an `HttpOnly`/`Secure`/`SameSite=Lax`/`__Host-`-prefixed cookie), for instant revocation ("log out everywhere" = one DB delete) and because it settles the SSE/EventSource cookie question for free (§3.3). Touches: API auth middleware, event-log.md §5.12 SSE authz, CSRF design.

3. **CSRF: synchronizer token, or `SameSite=Strict` alone?** Options: synchronizer token on every state-changing request (OWASP default), or Go 1.25 `http.CrossOriginProtection` (Fetch Metadata + Origin fallback, §3.2) with `SameSite=Lax` and no state-changing GETs. Touches: API middleware, frontend fetch wrapper, SSE Origin check (streaming.md).

4. **CLI auth: Device Authorization Grant (RFC 8628), and shared with the web Login Session model?** Proposed: yes — CLI does RFC 8628 against the same backend, gets a long-lived token revocable the same way a Login Session is, stored via `99designs/keyring` (fallback: file with a loud warning, like `gh`'s behavior). Touches: CLI roadmap item, Slash Command registry sharing (product.md), token/session table design.

5. **Invite-only signup and admin bootstrap: how is the first admin created, and how are subsequent friends invited?** Proposed: first successful login/registration (race-safe, transactional) becomes the sole admin; after that, admin-generated invite links (or an email allowlist an admin edits) gate every further signup — no public self-serve signup ever, matching the "friends" scale. Touches: `users` table (needs a role/admin flag that doesn't exist yet), CONTEXT.md Quota ("set by an admin" — this is where that admin comes from), settings UI.

6. **Provider Key envelope encryption: one DEK per row, or does `JF_MASTER_KEY` encrypt the Provider Key directly with AAD, no separate DEK?** **Decided 2026-09-27: one layer, no DEK** ([auth-keys.md](../design/auth-keys.md)); product.md and mcp-client.md reworded. ⚠ Review note: product.md and mcp-client.md §3/D7 already said "envelope-encrypted", which means a DEK wrapped by the master key; dropping the DEK would change those docs. Original proposal: no separate DEK in the base version — `JF_MASTER_KEY` (or its `key_id`-tagged successor) directly AES-256-GCM-encrypts the Provider Key with AAD `(user_id, provider)`; a DEK-per-row is the more "correct" enterprise pattern (§6.1) but adds a key-wrapping layer this scale doesn't need yet, and can be added later behind the same `key_id` interface without a data migration surprise (the row already stores `key_id`). Touches: `provider_keys` table (doesn't exist yet — should mirror `connector_credentials`'s shape), the shared encryption helper mcp-client.md already needs.
7. **Do we build custom crypto with Go's `crypto/cipher`, or take a dependency on Tink?** Proposed: `crypto/cipher` directly (already the language's own AEAD primitive, no new dependency, matches "deep Go" learning goal from product.md), revisit Tink only if key-rotation bookkeeping across many `key_id`s gets unwieldy by hand. Touches: the shared encryption helper (same one as Q6).

8. **Provider Key masking and deletion UI**: confirm "last 4 chars shown, full delete removes the row" as the pattern (§6.7) — this doc found no reason to deviate. Touches: Provider Key settings UI, provider-gateway.md §8 (already shows "Key rejected" on save failure; add the masked-display and delete-confirmation copy here).

9. **Rate limiting and lockout for login**: what threshold and window? Proposed: lock the *account* (not IP) after a small number of failed OTP/password attempts within a short rolling window (OWASP's own cheat sheet gives no fixed number — this needs a friends-scale-appropriate pick, e.g. 5 attempts / 15 minutes, tunable later like other jelly-fish thresholds). Touches: login endpoint, any password/OTP path chosen in Q0.
