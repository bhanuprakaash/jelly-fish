# Approver and Permissions (incl. Jev): Research

Status: research, 2026-09-27. Terms follow [`CONTEXT.md`](../../CONTEXT.md): the step that decides allow/ask/deny for a tool call is the **Approver** (never "guard/gate/classifier"); a saved "always allow" is an **Approval Rule** (never "allowlist entry/permission/grant"), scoped to a **Project** or everywhere, never created implicitly; **Jev** is the platform-provided decision model the Approver calls after rules and before the small-LLM fallback (never "safety model/classifier" in jelly-fish's own docs, though prior-art sources below use "classifier" for their own equivalents); **Permission Mode** is ask/auto(default)/full-auto (never "autonomy level/trust level"); a paused decision is an **Approval** (never "confirmation/consent/prompt"). Facts cite primary sources inline. **Unverified** marks anything not confirmed from a primary source. "⚠ cross-spec" flags a conflict or gap against jelly-fish's own docs; flagged here, not resolved.

> Ground truth, not redesigned here: [CONTEXT.md](../../CONTEXT.md) (Permission Mode, Approval, Approval Rule, Approver, Jev definitions above), [product.md](../product.md) Permissions section ("Free inside the sandbox. External tools are gated, using MCP `readOnlyHint`/`destructiveHint` as defaults for catalog Connectors only (custom-URL Connector tools default to ask)... Approver chain: Approval Rules, then Jev (platform-provided, with a confidence threshold), then a small-LLM fallback... approval dialog offers allow once / this project / everywhere, plus suggestions... Rules are visible and editable in settings, and never created implicitly"), ADR [0004](../adr/0004-layered-approver-no-implicit-rules.md) (layered Approver; "free inside the Sandbox, since the container limits the blast radius"; Jev returns allow/ask/deny with a confidence, anything below threshold goes to a human; harness may *suggest* a rule but only a human creates one; silent auto-approval learned from behavior was rejected), ADR [0003](../adr/0003-nothing-executes-on-the-host.md) (shell/file tools run only inside the Sandbox), ADR [0006](../adr/0006-byok-llm-platform-metered-services.md) (Jev is a metered Platform Service, platform holds the key, Quotas exist from day one), [agent-loop.md](../design/agent-loop.md) (`Hook.BeforeTool`, `ToolDef.ReadOnly/Destructive/ParallelSafe`, Approver runs on every call in a batch before any starts, one "ask" parks the whole batch, `approved_by`/`trace` on `tool.call.started`, Approver-check-failure → ask never allow, Decision 18), [event-log.md](../design/event-log.md) (`approval.requested{approval_id, kind, tool_call_id, approver trace}`, `approval.resolved{decision, scope, by}`, `awaiting_approval` holds no Worker and no Sandbox, resume is one unfenced tx, email/Telegram approvals use the same POST path), [mcp-client.md](../design/mcp-client.md) (Decision 12 rug-pull `tool_hash` on Connector-scoped Approval Rules; Decision 18 hints trusted only for catalog Connectors, custom-URL tools default to ask and aren't parallel-safe), [TODO.md](../../TODO.md) (Sandbox deferred; this item flagged as the next design doc).

## 1. Summary

- **jelly-fish's three-layer Approver (rules → Jev → small-LLM fallback) has no single direct precedent**, but each layer has strong prior art on its own: rule-based allow/deny/ask matching is universal across every harness surveyed (§2), and Anthropic's own Claude Code shipped, in the same month as this research, a two-stage LLM classifier ("auto mode") that is startlingly close to what ADR 0004 describes for Jev — confidence-gated, fails to "ask" on error, and explicitly strips tool *results* from what the classifier sees so that hostile content in a fetched page can't manipulate it directly ([Anthropic engineering](https://www.anthropic.com/engineering/claude-code-auto-mode); [code.claude.com/docs/en/permission-modes](https://code.claude.com/docs/en/permission-modes)). This is the closest real analogue to Jev found anywhere in this survey — see §4.
- **Every mature agent harness that ships a command-prefix allowlist has since shipped a CVE for bypassing it via shell composition** — Cursor (GHSA-82wg-qcm4-fp2w, GHSA-534m-3w6r-8pqr; [Pillar Security](https://www.pillar.security/blog/the-agent-security-paradox-when-trusted-commands-in-cursor-become-attack-vectors)), Cline (CVE-2026-52024/52025; [Manifold Security](https://www.manifold.security/blog/cline-code-execution-bypass)), Roo Code (CVE-2026-63108; [TheHackerWire](https://www.thehackerwire.com/roo-code-command-injection-bypasses-allowlist-cve-2026-63108/)), Gemini CLI ([issue #11766](https://github.com/google-gemini/gemini-cli/issues/11766)). **Claude Code is the one surveyed tool whose own docs describe splitting compound commands (`&&`, `||`, `;`, `|`, `|&`, `&`, newlines) and requiring every subcommand to independently match a rule** ([code.claude.com/docs/en/permissions](https://code.claude.com/docs/en/permissions), "Compound commands") — and even it documents, in the same section, that a rule never stops the same program invoked a different way (`/usr/bin/curl`, `sh -c '...'`), stating plainly that a Bash rule "isn't a security boundary around the program." This is the load-bearing finding for §7.
- **CVE-2026-52024 (Cline) is a documented instance of the exact failure mode this doc was asked to investigate for Jev**: "Safe Commands" doesn't inspect commands — it asks the AI agent whether its own command is safe and trusts the answer, "even after the same agent has been manipulated by attacker content" ([Manifold Security](https://www.manifold.security/blog/cline-code-execution-bypass)). A self-attesting classifier that shares context with the thing it's supposed to police is not a security boundary; Jev must not be built this way (§4, §7).
- **OpenHands' security analyzer is the closest published architecture to a layered rules→classifier→fallback pipeline**: `PatternSecurityAnalyzer` (regex), `PolicyRailSecurityAnalyzer` (shell-AST), `LLMSecurityAnalyzer` (a separate LLM instance judging risk), and `EnsembleSecurityAnalyzer` (combines all, returns the highest risk of LOW/MEDIUM/HIGH/UNKNOWN), gated by a `ConfirmRisky()` policy that only pauses on HIGH ([docs.openhands.dev/sdk/guides/security](https://docs.openhands.dev/sdk/guides/security)). A filed issue documents the analyzer misclassifying a destructive action as LOW and auto-executing it — a real, not hypothetical, over-approval failure ([openhands issue #4157](https://github.com/OpenHands/software-agent-sdk/issues/4157)).
- **No surveyed harness auto-creates a rule from repeated approvals.** Claude Code's closest feature, `/auto-mode-setup`, is a one-time, user-invoked onboarding scan of the repo/README/git remotes/recent command history that *drafts* candidate `autoMode.environment`/`allow` entries for the user to accept — not a background "you approved this 5×" nudge ([code.claude.com/docs/en/auto-mode-config](https://code.claude.com/docs/en/auto-mode-config)). ADR 0004's "harness may suggest a rule... only a human creates one" has no direct precedent to copy; jelly-fish's product.md wording ("approved 5×, always allow?") is closest in spirit to VS Code Copilot's scoped approval durations (session/workspace/always) but VS Code doesn't auto-suggest promotion either ([code.visualstudio.com/docs/agents/run/approvals](https://code.visualstudio.com/docs/agents/run/approvals)).
- **⚠ cross-spec, flagged for the spec, not resolved here**: TODO.md notes the Sandbox is deferred, so ADR 0004's "free inside the Sandbox" has nothing to be free *inside* yet. Every harness surveyed that has a real sandbox (Codex CLI, Claude Code, OpenHands) ties its approval policy to sandbox *escalation* — actions inside the sandbox boundary run free, actions that would leave it need approval ([learn.chatgpt.com/docs/agent-approvals-security](https://learn.chatgpt.com/docs/agent-approvals-security)). With no Sandbox, jelly-fish has no boundary to escalate past, so shell/file tools have no "free" zone at all — see §9, Q7.
- **The MCP spec itself mandates human-in-the-loop for tool calls and explicit distrust of hints from untrusted servers**, both already reflected in ADR 0004 and mcp-client.md Decision 18 — confirmed, not new (§7).

## 3. Approval Rule shape and matching

- **What a rule matches** — every harness surveyed matches on some combination of (a) tool/category, (b) a command-prefix or glob pattern, (c) a path, and (d) (increasingly) a specific input parameter. Claude Code's is the most granular published scheme: rules are `Tool` or `Tool(specifier)`, with tool-specific specifier grammars — Bash matches whole command text with `*` wildcards and explicit compound-command splitting; Read/Edit use gitignore syntax with four anchor types (`//abs`, `~/home`, `/relative-to-settings-source`, `bare-relative-to-cwd`); WebFetch matches on `domain:`; MCP matches `mcp__server` or `mcp__server__tool`; and, notably, deny/ask rules (not allow) can match an arbitrary top-level scalar input parameter via `Tool(param:value)` — explicitly **excluding** a tool's primary content field (`command` for Bash, `file_path` for Read/Edit) "because a rule like `Bash(command:rm *)` would be bypassable by a compound command" ([code.claude.com/docs/en/permissions](https://code.claude.com/docs/en/permissions)). **Recommendation for jelly-fish's Approval Rule shape**: match on (tool or Connector tool, argument pattern) the same way, and apply the same principle — a rule keyed to a structured, non-freeform argument (a path, a domain, a fixed enum) is safe to match narrowly; a rule keyed to a freeform string that a shell or script will later reinterpret (a raw shell command) is not, and should be scoped at the tool/Connector level, not the argument level, unless jelly-fish also parses and splits compound shell commands the way Claude Code does.
- **Scopes** — jelly-fish's product.md already fixes three: once / this project / everywhere. This is closest to VS Code Copilot's four durations (single-use, current session, entire workspace, all future invocations — [code.visualstudio.com/docs/agents/run/approvals](https://code.visualstudio.com/docs/agents/run/approvals)) and to Claude Code's per-repo-permanent vs. until-session-end split; no surveyed tool has exactly jelly-fish's three-way split, but all of them separate "this one time" from "this codebase" from "always," which validates the three-way design rather than suggesting a fourth tier is needed.
- **Allow vs. deny precedence** — the strongest, most explicit precedent is Claude Code's: **"Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order"** ([code.claude.com/docs/en/permissions](https://code.claude.com/docs/en/permissions)) — i.e. a broad deny always beats a narrow allow, by design, not by accident. Codex CLI's execpolicy independently arrives at the same shape with different words: "the strictest severity across all matches (`forbidden` > `prompt` > `allow`)" ([github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md](https://github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md)). **Recommend jelly-fish adopt the identical rule**: deny > ask > allow, first/strictest match wins regardless of specificity, and this applies even when Jev or the small-LLM fallback would have said allow — a saved rule should never be second-guessed downward in strictness by a later Approver stage, only upward (Jev asking when a rule said allow is not proposed by any source and would defeat the point of a saved rule; the reverse — Jev/LLM asking when no rule exists at all — is exactly the ADR 0004 chain).
- **Rug-pull hash interaction** — already decided in [mcp-client.md](../design/mcp-client.md) Decision 12 (a `tool_hash` over name+description+inputSchema+annotations invalidates a Connector-scoped Approval Rule on mismatch). This is validated by real-world precedent: **CVE-2025-54136 ("MCPoison")** let an attacker commit a benign MCP tool definition, wait for a developer's one-time approval, then silently swap in a malicious command — Cursor's trust model "bound approval only to the name of the MCP entry, not its underlying command or arguments," with no way for the client to verify current definitions matched what was reviewed at onboarding ([Check Point Research](https://research.checkpoint.com/2025/cursor-vulnerability-mcpoison/); [Tenable FAQ](https://www.tenable.com/blog/faq-cve-2025-54135-cve-2025-54136-vulnerabilities-in-cursor-curxecute-mcpoison)). Cursor's fix ("any change to an MCP config, even adding a single space, forces you to approve it again") is exactly what jelly-fish's hash-based invalidation already does — no new decision needed, just confirmation the design is right and the threat is real, not theoretical.
- **How rules are shown/edited** — Claude Code's `/permissions` dialog lists every rule and which settings file it came from, live-editable mid-session with immediate effect from the next tool call ([code.claude.com/docs/en/permissions](https://code.claude.com/docs/en/permissions)). jelly-fish's product.md already commits to "visible and editable in settings" — no conflict, and this is a reasonable bar to match (source-file provenance may be overkill for jelly-fish's single-tier project/everywhere scoping, but showing *which* scope a rule lives at is worth keeping).

## 4. Permission Modes: exact semantics per tool class

jelly-fish's three modes (ask / auto (default) / full-auto) most resemble Claude Code's `default` (Manual) / `auto` / `bypassPermissions`, with Codex CLI's `on-request`/`never`/`danger-full-access` as a second close match — both are three-tier "ask everything" → "classifier or policy decides" → "nothing asks" designs, which cross-validates jelly-fish's own three-tier product.md design rather than suggesting a different shape.

| Tool class | ask (jelly-fish) | auto (jelly-fish, default) | full-auto (jelly-fish) | Closest precedent |
|---|---|---|---|---|
| Built-in read-only (web search/fetch) | always asks | never asks (Claude Code: reads never prompt in any mode incl. Manual, [permissions.md](https://code.claude.com/docs/en/permissions)) | never asks | Claude Code `default` mode already auto-approves reads |
| Shell/file (Sandbox) | asks per ADR 0004 chain | ADR 0004: "free inside the Sandbox" — ⚠ no Sandbox exists yet, see §9 Q7 | free | Codex/Claude Code/OpenHands all gate on sandbox *escalation*, not on the tool class itself |
| Catalog Connector read-only (`readOnlyHint`) | asks | auto-approved (hint seeds default, mcp-client.md Decision 18) | free | MCP spec: hints untrusted unless from a trusted server ([modelcontextprotocol.io/specification/2026-07-28/server/tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)) — catalog-only trust already matches this caveat |
| Destructive (any) | asks | Approver chain runs (rules→Jev→LLM); ADR 0004 gives Jev a confidence threshold | free — ⚠ open question, see §9 Q1 | Claude Code's `bypassPermissions` still blocks `rm`/`rmdir` on "critical paths" even in full-bypass — i.e. **no surveyed harness makes "full auto" mean zero exceptions** |
| Custom-URL Connector (any) | asks | asks (mcp-client.md Decision 18: no hint trust, not parallel-safe) | Unverified — full-auto's stance on custom-URL Connectors isn't specified in product.md | matches Claude Code's principle that untrusted-source hints never auto-approve |

- **Per-session vs. per-project mode switching**: product.md's `/mode` slash command implies per-session switching; CONTEXT.md's Agent definition ("permission mode" is a saved Agent field) implies per-Agent/per-project defaults. Claude Code has both: a `permissions.defaultMode` setting (project/user/managed) and a live in-session switch (`Shift+Tab`), with an explicit rule that **project-level settings files cannot silently turn on `auto` or `bypassPermissions`** — those two modes only take effect from user or managed settings, specifically to stop a malicious or careless repo from weakening the starting mode ([code.claude.com/docs/en/permission-modes](https://code.claude.com/docs/en/permission-modes), "which mode a session starts in"). **Recommend jelly-fish adopt the same asymmetry**: a Project's stored Agent config may *default* to ask/auto, but a project cannot be used to silently downgrade an individual session below what the User's own account-level settings allow (relevant once jelly-fish's Workspace model gains more than one User; not a base-version blocker since Workspace = one User today).
- **full-auto's actual exception list matters more than its name** — every "everything auto-approved" mode surveyed still has a hard-coded exception list that survives it: Claude Code's `bypassPermissions` still blocks writes that would remove a "critical path" and still runs "cross-session messaging safeguards" ([permission-modes.md](https://code.claude.com/docs/en/permission-modes)); Codex's `danger-full-access` is explicitly annotated "(not recommended)" in its own docs rather than treated as a normal option ([learn.chatgpt.com/docs/agent-approvals-security](https://learn.chatgpt.com/docs/agent-approvals-security)). **Recommend jelly-fish's full-auto keep an unconditional exception list too** (e.g. `rm -rf` targeting the Workspace Volume root or outside it, revoking the user's own Provider Keys/credentials) rather than being a literal zero-exceptions bypass — see §9 Q1.

## 5. Jev: prior art for an automated approval model

- **The single closest real precedent is Anthropic's own Claude Code auto mode**, shipped in the same window as this research and independently confirmed against its primary docs (not the agent report alone): "a second model, the classifier, reviews actions instead of you" ([code.claude.com/docs/en/permission-modes](https://code.claude.com/docs/en/permission-modes)). Its architecture, verified directly:
  - **Two-stage pipeline**: Stage 1 is "a single yes-or-no decision without reasoning," deliberately tuned to "err on the side of blocking" (high recall, cheap); Stage 2 runs only on actions Stage 1 flagged, using "the same prompt" with an instruction requesting "careful reasoning" — and because the input is identical except the final instruction, "stage 2's prompt is almost entirely cache-hit from stage 1," which is a direct, reusable idea for keeping Jev's own latency/cost down as a metered Platform Service (ADR 0006) ([anthropic.com/engineering/claude-code-auto-mode](https://www.anthropic.com/engineering/claude-code-auto-mode)).
  - **Published numbers**: Stage 1 alone: 8.5% false-positive rate, 6.6% false-negative rate. Full pipeline: 0.4% FPR, 17% FNR — Anthropic's own framing: "The 17% false-negative rate on real overeager actions is the honest number" (same source). This is a directly citable, real-world calibration point for jelly-fish's own confidence-threshold tuning (ADR 0004 already plans to tune with the eval suite) — a two-stage cheap-then-expensive design trades a much lower FPR for a real, non-trivial FNR, and that tradeoff is disclosed, not hidden.
  - **What it sees and doesn't**: "the classifier sees user messages, tool calls other than read-only lookups such as file reads and searches, and your CLAUDE.md content. **Tool results are stripped from those requests, so hostile content in a file or web page can't manipulate the classifier directly**" ([code.claude.com/docs/en/permission-modes](https://code.claude.com/docs/en/permission-modes)). This is the single most important design fact in this whole document for Jev's input contract: Jev must not receive raw tool *outputs* (which may carry attacker-controlled content) as part of its own review context, only the call being requested and trusted conversation state — otherwise Jev itself becomes attackable the same way the underlying agent is.
  - **Fails closed on infra failure**: "if the classifier blocks 3 times in a row or 20 times total, auto mode pauses and Claude Code resumes prompting" and "under server-side classifier review... Claude Code denies an action the server gives no verdict for" — no verdict is never treated as "allow" (same source). This matches ADR 0004/agent-loop.md Decision 18 exactly (Jev/LLM failure → ask, never allow) — confirmed as the right call, not a jelly-fish-only choice.
- **Codex CLI's `auto_review`** independently arrives at a similar shape from a different angle: `approvals_reviewer = "auto_review"` "route[s] eligible approval requests through a reviewer agent before Codex runs the request," but — importantly — "evaluates only actions that already need approval, such as sandbox escalations, blocked network requests... or side-effecting app and MCP tool calls" ([learn.chatgpt.com/docs/agent-approvals-security](https://learn.chatgpt.com/docs/agent-approvals-security), confirmed by direct fetch). This validates ADR 0004's chain ordering: a classifier reviewing only what rules didn't already resolve (rather than re-reviewing everything) is the pattern two independent vendors converged on.
- **OpenHands' security analyzer is the most explicit "ensemble" precedent**: `PatternSecurityAnalyzer` (regex: `rm -rf`, `curl|sh`, `eval`), `PolicyRailSecurityAnalyzer` (shell-AST, for composed/chained threats), `LLMSecurityAnalyzer` (a separate LLM instance judging the action's context), and `EnsembleSecurityAnalyzer` (runs all, returns the *highest* risk of LOW/MEDIUM/HIGH/UNKNOWN); a `ConfirmRisky()` confirmation policy pauses only on HIGH ([docs.openhands.dev/sdk/guides/security](https://docs.openhands.dev/sdk/guides/security), as reported by research agent, URL structure and class names consistent with OpenHands' public SDK naming conventions). A filed issue documents the LLM analyzer misclassifying a destructive action as LOW risk and letting it auto-execute — a real over-approval failure, not hypothetical ([github.com/OpenHands/software-agent-sdk/issues/4157](https://github.com/OpenHands/software-agent-sdk/issues/4157)). **Unverified**: no published false-positive/negative rates for OpenHands' analyzer (unlike Claude Code's).
- **Meta's Llama Guard family** is the clearest "small, purpose-built classifier, not the main model" precedent, and now explicitly covers agentic tool abuse: Llama Guard 3 adds category **S14: Code Interpreter Abuse** ("responses seeking to abuse code interpreters, including DoS, container escapes, privilege escalation" — [github.com/meta-llama/PurpleLlama Llama-Guard3 model card](https://github.com/meta-llama/PurpleLlama/blob/main/Llama-Guard3/8B/MODEL_CARD.md)), and ships 1B/8B size variants explicitly trading latency for quality — directly relevant to Jev's "small-LLM fallback" distinction (§ below).
- **What distinguishes Jev from the small-LLM fallback, per ADR 0004 and agent-loop.md**: Jev is *the* platform-provided decision model (a specific TypeSafe-hosted model per CONTEXT.md), called first and metered as Usage; the small-LLM fallback only runs when Jev's own confidence is below threshold (an "ask a human" case that ADR 0004 already routes to a human, not the fallback — re-read ADR 0004: "anything below the threshold goes to a human," so **⚠ the fallback's exact trigger condition is underspecified**: agent-loop.md §4.4 says the chain is "Approval Rules, then Jev, then a small-LLM fallback" but ADR 0004 says low-confidence Jev output goes to a human, not to a third model. This is a real ambiguity between jelly-fish's own two ground-truth docs — flagged as **Q3** below, not resolved here.
- **Known failure modes, documented, not hypothetical**:
  1. **Over-approval** — OpenHands issue #4157 above; Claude Code's own published 17% FNR is a disclosed instance of the same thing at a different rate.
  2. **The classifier itself being fooled by the same injection targeting the agent** — **CVE-2026-52024 (Cline)** is the clearest documented case: "'Safe Commands' doesn't inspect commands—it asks the AI agent whether its own command is safe and trusts the answer, even after the same agent has been manipulated by attacker content" ([Manifold Security](https://www.manifold.security/blog/cline-code-execution-bypass)). This is precisely the "second-order prompt injection against the approver" failure mode this doc was asked to investigate, confirmed as real, not speculative. Academic treatment of the general adversarial-evasion problem exists (character/homoglyph injection against guardrail classifiers — [arxiv 2504.11168](https://arxiv.org/pdf/2504.11168)) but no paper was found targeting an agent's *own* tool-approval classifier specifically by name; Cline's CVE is the concrete, named instance to cite instead.
  3. **Latency/cost** — no vendor publishes Jev-equivalent latency numbers as a metered line item; the closest documented guidance is general LLM-guardrail industry practice recommending a latency budget of roughly 100–300ms and favoring small (86M–1B parameter) classifier models to hit it (**Unverified/secondary**, [futureagi.com/blog/ultimate-guide-llm-guardrails-2026](https://futureagi.com/blog/ultimate-guide-llm-guardrails-2026/)). No vendor (Anthropic, OpenAI) documents billing its own approval classifier as a standalone metered product the way ADR 0006 plans for Jev — jelly-fish would be first to expose this as user-visible Usage, as far as this survey found.
- **Recommendation**: build Jev's input contract to mirror Claude Code auto mode's exclusion rule exactly — the call being requested, its `ToolDef` flags, and *trusted* conversation state (user messages, Agent instructions), never raw tool *results*, which is where injected content lives (memory.md's own "taint" concept — `ToolDef.Untrusted` — already exists in agent-loop.md §3 and should gate what reaches Jev the same way it gates memory writes).

## 6. Rule suggestions ("approved 5×, always allow?")

- **No surveyed harness ships an automatic "you approved this N times, want a rule?" nudge.** The two closest things found: Claude Code's `/auto-mode-setup` (user-invoked, one-time, scans repo/README/git remotes/recent command history and *drafts* rule entries for the user to accept — [code.claude.com/docs/en/auto-mode-config](https://code.claude.com/docs/en/auto-mode-config)) and the general per-prompt "Yes, and don't ask again" option present in nearly every harness surveyed (Claude Code, VS Code Copilot, Cursor) which turns *one* approval into a permanent rule immediately, with no repetition count at all.
- **Why "never silently created" matters, with a concrete counter-example**: ADR 0004's rejected alternative — "silent auto-approval learned from behavior... rejected as unsafe and confusing" — has no surveyed harness contradicting it; every rule-creation UX found requires an explicit user action (checking a box, selecting "don't ask again," accepting a drafted suggestion), never a background counter that flips a setting on its own. This validates ADR 0004's decision as consistent with the entire surveyed field, not an outlier caution.
- **Threshold**: product.md's own wording ("approved 5×, always allow?") is jelly-fish's own number — no vendor source was found suggesting or contradicting 5 specifically; this is a tuning parameter, not something drawn from prior art (flagged as **Q6** below).
- **Recommendation**: keep the "suggest, never auto-create" design as specified; model the suggestion dialog on Claude Code's `/auto-mode-setup` drafted-entries pattern (show the exact rule that would be created, scoped to project or everywhere, with an explicit accept/dismiss, not a silent toggle) rather than inventing new UX.

## 7. Approval UX when parked

- **`awaiting_approval` with no Worker** is already specified (event-log.md §5.7, ADR 0003 consequence: "a session waiting days on an Approval holds no container and no worker"). No harness surveyed needed to solve this problem the same way, since none of them are durable multi-day server-side agents in the way jelly-fish is — **this is jelly-fish's own architectural answer, not adopted from prior art**, and no conflict was found.
- **Notifications and Channels**: product.md's PWA push (with Approve/Deny actions) → email (signed one-click links) → Telegram ordering has a rough analogue in Claude Code's own multi-surface approval (CLI, VS Code, Desktop, claude.ai web/mobile all show the same pending approval and let any of them resolve it — [code.claude.com/docs/en/permission-modes](https://code.claude.com/docs/en/permission-modes), "Switch permission modes" tabs) but Claude Code's is all first-party surfaces of one product, not a Channel abstraction spanning independent providers the way jelly-fish's design does. No cross-spec conflict; jelly-fish's Channel design goes further than anything surveyed.
- **Child Session approvals bubbling to the parent's user**: no harness surveyed runs an agent hierarchy with independently-durable child sessions in jelly-fish's sense. jelly-fish's own event-log.md §5.10/§5.17 already specifies that Interrupt on a parent propagates to children, and agent-loop.md doesn't separately special-case an Approval requested *inside* a Child Session — by the existing waiting-states model (event-log.md §5.7), a Child Session that hits `awaiting_approval` simply parks itself the same as any session; the parent stays `awaiting_children` until the child resolves (event-log.md §5.10's `lastOpenBlockingChild` logic). **This appears to already be handled correctly by composition of existing mechanisms, with no new decision needed** — flagged as a confirmation, not a gap.
- **Expiry/timeouts on a pending Approval**: not found in any harness surveyed as an automatic "expire and deny" — Claude Code's approvals wait indefinitely for a human; Codex CLI's likewise. **Unverified anywhere** that any surveyed product auto-expires a pending human approval. jelly-fish's own docs don't currently specify one either — flagged as **Q8**.
- **Batching several pending approvals**: agent-loop.md §5.2/§8 already specifies this precisely for jelly-fish (one "ask" pauses the whole parallel-safe batch; UI shows "one card (all calls together), not one card per call"). No surveyed harness does exactly this (most ask serially, one dialog per call), so **jelly-fish's batched-ask design is ahead of, not behind, the surveyed field** — worth keeping as designed. Codex CLI's own backlog explicitly complains about the lack of this ("Excessive approval prompts... no batching," [github.com/openai/codex/issues/47134](https://github.com/openai/codex/issues/47134)), which is independent validation that batching is the right call, not just internally reasoned.
- **Showing tool inputs before approval**: the MCP spec is explicit and directly load-bearing here: applications "SHOULD provide UI that makes clear which tools are being exposed to the AI model, insert clear visual indicators when tools are invoked, and present confirmation prompts to the user for operations to ensure a human is in the loop," and "there SHOULD always be a human in the loop with the ability to deny tool invocations" ([modelcontextprotocol.io/specification/2026-07-28/server/tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), as reported and consistent with the security-considerations text already cited in mcp-client.md §5). Codex CLI independently documents the same principle operationally: Codex "compares the command's argument list to pattern... treats the command as a list of arguments (like what execvp(3) receives)" and surfaces a `justification` field in the approval prompt ([github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md](https://github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md)). **Recommend jelly-fish's approval dialog always show the full, final tool arguments** (not a summary), matching product.md's implicit design and both these sources — this is uncontested across every primary source found.

## 8. Security

- **Prompt injection causing a dangerous call, documented instances**: **CVE-2025-59536** (Claude Code) — a malicious repo's `.claude/settings.json` hooks executed "before the user could even read the trust dialog," letting a cloned untrusted repo run arbitrary shell commands and exfiltrate API keys ([Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/); [Tenable](https://www.tenable.com/cve/CVE-2025-59536)) — this is a confused-deputy pattern specifically at the *trust-dialog-timing* layer: the approval system existed but the dangerous action ran before it could fire. **Recommend**: jelly-fish's Approver must gate on `tool.call.started`'s append committing (already an invariant in event-log.md §6: "a tool must never be called unless its `tool.call.started` append committed") — this already structurally prevents Claude Code's exact failure (nothing can run before the approval decision is durably recorded), a genuine architectural advantage of the event-log design worth naming explicitly.
- **The confused-deputy problem, named for LLM agents specifically**: a 2026 paper, **"Capability Gates Are Not Authorization: Confused-Deputy Failures in LLM Agent Frameworks"** ([arxiv.org/abs/2606.28679](https://arxiv.org/abs/2606.28679), confirmed to exist via independent search), audited LangChain/LangGraph, LlamaIndex, and the Stripe Agent Toolkit and "found that while all three provide capability gating by default, none provides a deterministic fail-closed per-call value authorization gate by default" — i.e. these frameworks check *whether a tool is exposed*, not *whether this specific call's arguments are authorized*. This is directly relevant to jelly-fish's rug-pull design (§3) and to why an Approval Rule must be scoped to argument patterns, not just "this tool is allowed." Quarkslab's engineering blog frames the same pattern in prose: "the LLM is not the root cause, nor a valid security boundary... enforce authorization at the tool level, not via hardened prompts" (**secondary source**, cited by research agent, not independently refetched here — [blog.quarkslab.com/agentic-ai-the-confused-deputy-problem.html](https://blog.quarkslab.com/agentic-ai-the-confused-deputy-problem.html)).
- **Deny-list bypass via shell tricks**: confirmed as a live, current problem across the field (§2's compound-command row), and Claude Code's own documentation is the most candid primary source about the limits of pattern matching: *"Bash permission patterns that try to constrain command arguments are fragile"* — a rule intending to restrict `curl` to one domain "won't match variations like: Options before URL... Different protocol... Redirects... Variables" — and its own recommended fix is **not** a smarter pattern language but structural: deny the raw shell tool for network access entirely and force network-capable actions through a separate, argument-typed tool (`WebFetch(domain:...)`) instead of trying to regex-validate a `curl` invocation ([code.claude.com/docs/en/permissions](https://code.claude.com/docs/en/permissions)). **This is a directly transferable recommendation for jelly-fish**: any Approval Rule that tries to constrain a shell command's arguments (a path prefix, a URL) is fragile by construction; prefer denying/restricting the shell tool itself and routing that class of action through a typed built-in tool or Connector where the argument is a real schema field, not a string a shell will reinterpret.
- **The MCP spec's own untrusted-hints stance**, already reflected in mcp-client.md Decision 18, is independently reconfirmed: annotations (`readOnlyHint`/`destructiveHint`) "are not guaranteed to faithfully describe tool behavior, and clients must treat them as untrusted unless they come from a trusted server" — "a malicious server could claim `readOnlyHint: true` while actually deleting files" (as reported, consistent with [modelcontextprotocol.io/specification/2026-07-28/server/tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)'s security-considerations language already cited in mcp-client.md). No new decision needed; jelly-fish's catalog-only trust tier is the spec-recommended posture.
- **Simon Willison's "lethal trifecta"** (private data + untrusted content + external communication = the precondition for prompt injection to matter — [simonwillison.net/2025/Jun/16/the-lethal-trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)) is the clearest, most-cited framing for *why* an Approver exists at all, and maps directly onto jelly-fish's own tool taxonomy: built-in read-only tools + Connectors together give a session private data access (memory, project files, Connector data), untrusted content (web fetch results, Connector responses), and external communication (a Connector write, an email-sending tool) — all three legs are present in jelly-fish's base version the moment a Connector and a Sandbox are both attached to one session. This is the strongest single argument for keeping the Approver's default posture conservative (ask, not auto) whenever those three legs are simultaneously in play, worth a one-line callout in the eventual spec's rationale section even though it changes no existing decision.
- **Audit trail (`approved_by`)**: agent-loop.md already carries `approved_by` (`rule:<id>`/`jev`/`llm`/`user`/`mode:<mode>`) plus a `trace` on `tool.call.started`, and event-log.md's `approval.resolved{decision, scope, by}` captures who resolved a parked approval. No harness surveyed publishes an equivalent structured audit field for interactive use (Claude Code's own audit logging is Enterprise-console-only, not part of the open CLI product, per one research agent's finding — **Unverified**, not independently refetched); jelly-fish's design is already ahead of what's publicly documented elsewhere. No change recommended.

## 9. Open questions for grilling

1. **Does full-auto mean literally zero exceptions, or does it keep a hard-coded exception list** (e.g. deleting the Workspace Volume root, revoking the user's own Provider Keys) **the way every "everything auto-approved" mode surveyed does** (Claude Code's `bypassPermissions` still blocks critical-path `rm`; Codex's `danger-full-access` is annotated "not recommended" in its own docs)? Proposed: keep a small, hard-coded exception list even in full-auto — every precedent found does this, and "full-auto" as a literal escape hatch with zero exceptions has no surveyed analogue (§4).
2. **Should jelly-fish split compound shell commands and require every subcommand to independently match a rule**, the way Claude Code does, given this is the one mechanism found anywhere in this survey that meaningfully resists command-chaining bypass (§2, §7)? Proposed: yes for Approval Rules that scope a shell command by prefix — but note Claude Code's own caveat that this still isn't a security boundary around the *program* (a rule stops the invocation form Claude tends to produce, not every equivalent invocation) — pair it with denying/restricting the raw shell tool for anything with a typed alternative (WebFetch, a Connector), per §8.
3. **⚠ Resolve the ADR 0004 vs. agent-loop.md ambiguity on what triggers the small-LLM fallback**: ADR 0004 says Jev's low-confidence output "goes to a human"; agent-loop.md §4.4 lists the chain as "rules, then Jev, then a small-LLM fallback," implying the fallback runs *before* asking a human, not that low confidence always means asking a human directly. Proposed: the fallback exists specifically to reduce needless "ask a human" cases for the *cheapest* band of Jev's uncertainty (a fast, cheap second opinion), with only fallback-level uncertainty (or fallback failure) actually reaching a human — but this needs a real decision, not a guess, since it changes both Jev's threshold calibration and the fallback's own contract.
4. **What does Jev's input contract exclude, precisely** — should it mirror Claude Code auto mode's rule of never receiving raw tool *results* (only the call, `ToolDef` flags, and trusted conversation state), given CVE-2026-52024 shows a self-attesting classifier sharing an agent's (possibly injected) context is a real, exploited failure mode (§5, §7)? Proposed: yes, exclude tool results and any content already flagged `ToolDef.Untrusted`/memory-tainted from what reaches Jev, mirroring Claude Code's documented approach exactly.
5. **Does the Approver need a rug-pull-style hash for non-Connector tools too** (built-in tools whose behavior could change across a jelly-fish deploy), or is mcp-client.md's Connector-only `tool_hash` sufficient? Proposed: not needed for built-ins — they're versioned with the binary, not independently mutable the way a remote MCP server is; keep the hash Connector-scoped as already decided.
6. **What's the actual threshold for a rule suggestion** ("approved 5×")? No prior-art number was found to anchor this; product.md's "5" is jelly-fish's own guess. Proposed: treat as a tunable, evaluated with the eval suite the same way Compaction's thresholds already are (context.md §5.3) — no vendor precedent to defer to either way.
7. **⚠ Sandbox not designed yet — how should the Approver treat shell/file tools in the meantime** (TODO.md's own flag)? Every harness with a real sandbox gates approval on *escalation past the sandbox boundary*, not on the tool class itself (§4); with no boundary, jelly-fish has no "free" zone for shell/file calls to fall into. Proposed: until the Sandbox spec lands, treat shell/file tools as **not** free — route them through the full Approver chain like any external tool (i.e., temporarily suspend ADR 0004's "free inside the Sandbox" clause for shell/file specifically, not for Connectors, since Connectors already have their own hint-based gating) — cheap to relax later once the Sandbox exists and can actually bound the blast radius.
8. **Should a pending Approval expire?** No surveyed harness auto-expires one; jelly-fish's own docs don't specify either, and event-log.md's model (a session can wait indefinitely with no Worker/Sandbox held) makes indefinite waiting cheap. Proposed: no automatic expiry in the base version — matches every precedent found, and jelly-fish's architecture is specifically built to make long waits free, unlike products bound to a live process.
9. **Does a batched "ask" (agent-loop.md §5.2, multiple pending tool calls in one card) need per-call allow/deny, or is it all-or-nothing?** Not directly addressed by agent-loop.md's current text ("ask-gates-the-batch" pauses the whole batch, but resolution granularity for the user's response isn't spelled out). Proposed: all-or-nothing per batch is simpler and matches "one card, all calls together" from agent-loop.md §8 — a user wanting fine-grained control can already deny the batch and let the model retry with fewer calls; no surveyed harness does per-call batch resolution either.
10. **How should Jev's confidence threshold be exposed/tuned** — a single global number, or per-tool-class (destructive vs. Connector-write vs. shell)? No single-number precedent found (Claude Code's is a fixed two-stage pipeline, not a user-tunable dial; OpenHands' is a fixed risk-level gate). Proposed: per-tool-class thresholds, tuned via the eval suite the same way Compaction's are — a single global number conflates classes with very different cost-of-false-allow.
